## 15. Acceptance Criteria

The system is accepted when all of the following are true. Each test cites the IDs of the criteria it verifies.

Every criterion carries exactly one tier marker:

- **`[crit]`** — **Critical**: a defect means data corruption, financial impact, authentication/authorization failure, data integrity violation, or misleading state that causes wrong user decisions. Verified by automated test. The method matches the contract's surface — unit, integration, E2E or a mix thereof.
- **`[vis]`** — **Visual / Design**: specifies expected behavior that does not guard a critical path. Verified by structural E2E as well as regular human review.
- **`[infra]`** — **Infrastructure / Structural**: a constraint on the deployed environment, the build pipeline, or the source-tree organization. Verified by deployment procedures, CI gates, lint, or code review — not by tests against the running system.

**IDs.** An ID's meaning never changes, and an ID is never reused.

- Split → the old ID retires; every part gets a new ID. A narrowed ID would keep stale citations resolving.
- Merge of duplicates → the survivor keeps its ID; the other retires.
- Delete → the ID retires.

**Shape.** One AC states one behavior, in one of these forms (EARS):

- `When <trigger>, the system <response>.`
- `If <unwanted condition>, the system <response>.`
- `While <state>, the system <response>.`
- `The system <property>.`

What an AC carries and where the rest goes: [index.md § Placement](index.md#placement).

### 15.7 Engineering

- **AC-32** `[infra]`: Code structure and dependency direction follow [architecture.md §11.2](architecture.md#112-responsibility-boundaries). No reverse imports.
- **AC-33** `[infra]`: Mutation boundary per [architecture.md §11.1](architecture.md#111-mandatory-constraints) is enforced. UI components dispatch through the state layer, not directly to the API client.
- **AC-34** `[infra]`: State configuration (labels, colors, thresholds) is centralized, not scattered.
- **AC-35** `[infra]`: Dependency direction is enforced by linter import restriction zones.
- **AC-36** `[infra]`: Linting and formatting pass.
- **AC-37** `[infra]`: Tests defined in section 16 pass. Push/PR gate runs unit, component, and API integration tests. E2E tests run nightly against the protected branch and on demand, and a failed run raises a tracked issue (see [architecture.md §11.7](architecture.md#117-continuous-delivery-pipeline)).
- **AC-343** `[infra]`: The role-permission matrix published in [api.md §14.3](api.md#143-authorization-rules) matches the codebase's authorization configuration — a CI-enforced check fails the build when the published table and the configuration diverge, and fails rather than passing vacuously when the table's delimiters are absent. Every role in that configuration is exhaustively classified as production-facing or test-only; an unclassified role fails CI. Only production-facing roles appear in the published matrix, and any other consumer of the production-role set derives it from the same classification rather than maintaining an independent list.
- **AC-349** `[infra]`: The per-role navigation matrix published in [ui/index.md §8.7.1](ui/index.md#871-views), and the first-match landing order published with it, match the route table — a CI-enforced check fails the build when the published content and the route table diverge, and fails rather than passing vacuously when its delimiters are absent. Each route declares its access rule as data, so the published matrix carries the rule itself (the required permission, or the admitted roles) alongside the role set that rule resolves to over the production role set; a route whose gate is a permission is not published as a bare list of today's role holders. The check covers the matrix and the landing order; the per-view prose around them is hand-authored.
- **AC-347** `[infra]`: Every file and called function cited in tracked documentation exists — a CI-enforced check fails the build on a citation of a renamed or deleted one. Three citation forms are claims: a repository path; a file name whose extension some tracked file carries, which resolves when a tracked path ends with it at a path-segment boundary, so a partial path (`routes/auth.ts`) singles out a name several files share; and a call-form identifier (`name()`), which resolves when its final name segment occurs as a whole word in a tracked file other than documentation. Line-number and symbol suffixes are stripped before a path resolves; an extensionless module reference resolves as the module it names. Globs and host paths (absolute, or prefixed `~/` or `./`) are not claims. Citations that name a nonexistent file or function on purpose — an illustrative walkthrough, a decision record naming what it superseded, a declared coverage gap, or a name outside the tracked tree (on a host, in a dependency or external project, built, or created at run time) — are exempted per document with a stated reason, so an exemption earned by one document does not cover the same citation elsewhere.
- **AC-348** `[infra]`: Every relative file link and `#anchor` fragment in tracked documentation resolves — a CI-enforced check fails the build on a broken internal link. Fragment resolution follows GitHub's heading-slug algorithm and honours inline HTML anchors, so a document that anchors a non-heading element is not reported broken. Links to directories that exist are valid. External and mail targets are not resolved: the check performs no network requests, so a third-party host cannot fail the build.
- **AC-351** `[infra]`: The OpenAPI document at `docs/api/openapi.json` is generated from the route definitions' declared request schemas, not hand-authored — a CI-enforced check fails the build when the published artifact and the route definitions diverge, and a second check fails the build when the generated document is not valid against the API-description format it declares. The document publishes only what the route definitions support: where a route declares no response, the published operation is silent about responses rather than asserting a default one. Its endpoint surface is complete for the API, enforced from both ends: every route a client calls is registered by the application factory, and a route registered anywhere else fails the build; and a registered route the document does not publish fails the build too, so a description tool that drops a route by default cannot silently shrink the published surface. A route excluded from the document declares that exclusion at its registration site. Serving the compiled front-end's own static files is the one exception, registered outside the factory and deliberately absent from the document; it is declared at the registration site, so it cannot grow silently. It is a derived view, not the contract — [api.md §14.2](api.md#142-operations) remains normative, which is why the artifact lives outside the spec directory.
- **AC-352** `[infra]`: The endpoint table published in `docs/api/README.md` is generated from the routes the application factory registers, not hand-authored — a CI-enforced check fails the build when the published table and the registered routes diverge. Every published column is read off the route itself: each access gate declares its rule as data, so the table carries the rule (the required permission keys, or the admitted roles) rather than a restatement beside it, and a session gate applied to a whole route group marks the routes it protects, so an endpoint is published as public because no gate reaches it and not because a hand-kept list says so. Endpoint prose outside the generated block is hand-authored and is not overwritten.
- **AC-353** `[infra]`: The generated OpenAPI document states, per operation, whether a session is required — derived from the access gates the routes themselves carry, not from a hand-kept list of public endpoints. The authentication scheme is declared once, and every published operation carries either that requirement or an explicit empty one, so an operation publishes as unauthenticated because no gate reaches its route and not because an allowlist says so. The derivation is total: a published operation the generator cannot trace back to a registered route fails the build, rather than publishing silently with no requirement at all — the fail-open direction, which would understate the protection the server actually enforces. A route whose only gate rejects unauthenticated callers without a session gate ahead of it fails the build for the same reason: it would publish as unauthenticated while refusing every caller.
- **AC-354** `[infra]`: The catalogue of machine-readable error codes published in [api.md §14.4.1](api.md#1441-error-categories) matches the single definition the server raises errors from — a CI-enforced check fails the build when the two diverge in either direction, and fails rather than passing vacuously when the catalogue's delimiters are absent. That definition has one runtime form, and the type every error response is constructed against is derived from it rather than restated beside it, so the set the API can emit and the set the contract declares cannot disagree. Every published code is minted by a named factory, so the contract cannot promise a code no factory produces. The check covers the set of codes; the per-code prose around it is hand-authored.
- **AC-380** `[infra]`: Every route the application factory registers under a method other than `GET` or `HEAD` is classified as versioned or exempt — a CI-enforced check fails the build on an unclassified route. Each exemption names its reason (e.g. no prior read, no shared editable row, own state check, a non-versioned case in [data-model.md §6.4](data-model.md#64-concurrency)). A self-test with a planted unclassified route goes red.
- **AC-383** `[infra]`: Every authenticated route the application factory registers whose access gates admit the worker role is either probed for worker data scoping ([ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md)) or exempt with a named reason. A CI-enforced check fails the build on a route that is neither. Probes run as a worker against seeded data: a request whose entity ids all belong to a project the worker is not assigned to is refused; a request naming an assigned project and a child entity of an unassigned one is refused; a read naming no entity returns no entity of an unassigned project. "Refused" means `403` or `404`, or `422` where the route's own AC rejects a foreign id as invalid input ([AC-414](#1526-attachments)). A self-test goes red on a planted route that skips the scope check, one that skips the parent binding, one that leaks an out-of-scope entity from a read, and one left unclassified.
- **AC-247** `[crit]`: Transport-layer rejections from the API server preserve the 4xx HTTP statusCode native to the failure class and ship a stable machine-readable code, per [api.md §14.4.2](api.md#1442-error-principles): a malformed body declared as `Content-Type: application/json` returns `400 VALIDATION_ERROR`; a payload exceeding the configured maximum returns `413 VALIDATION_ERROR`; a request whose `Content-Type` falls outside the accepted set returns `415 VALIDATION_ERROR`; a request whose method and URL match no registered handler returns `404 ROUTE_NOT_FOUND`. Pre-existing branches are unchanged: schema-validation rejections remain `422 VALIDATION_ERROR` (with the field-level `details` array preserved), rate-limit rejections remain `429 RATE_LIMITED`, and any error whose statusCode is in the 5xx range — or carries no statusCode — maps to `500 SERVER_ERROR`. Every 5xx response logs at the operational `error` level — an application error carrying its own 5xx code included, since answering 500 silently hides a genuine server failure from triage; transport-layer 4xx rejections log below that level. Tiered `[crit]` because the contract guards operator triage: a transport-layer 4xx surfacing as 5xx (response or log) misroutes oncall attention away from genuine server failures.
- **AC-1** `[vis]`: The full stack (frontend, backend, database) starts locally with a documented command or minimal command sequence.

### 15.11 Customer Management

- **AC-54** `[crit]`: Creating a customer with a name returns a customer object with a generated ID. Phone, email, address, and notes are optional.
- **AC-55** `[crit]`: Updating a customer changes only the specified fields (PATCH semantics). Passing `null` clears an optional field.
- **AC-56** `[crit]`: Listing customers returns all customers with pagination support. The `search` parameter filters by name (case-insensitive substring match).
- **AC-57** `[crit]`: Getting a customer returns the full customer object and a count of associated projects.
- **AC-58** `[crit]`: A project references a customer via `customerId`. The API returns the full customer object nested in project responses.
- **AC-91** `[crit]`: Deleting a customer with no active projects AND no issued or cancelled invoices on any of its archived projects succeeds (hard delete). Any archived projects are purged atomically with the customer; any draft invoices on those archived projects cascade-delete with the project. The customer no longer appears in list or get responses. Customers whose archived projects carry issued or cancelled invoices are rejected separately under [AC-307](#1511-customer-management).
- **AC-92** `[crit]`: Deleting a customer that has active (non-archived) projects is rejected as a conflict (per the conflict error category in [api.md §14.4.1](api.md#1441-error-categories)). The customer and its projects remain unchanged.
- **AC-93** `[crit]`: Deleting a customer requires `customer:delete` permission. Users without this permission receive an authorization error.
- **AC-154** `[crit]`: The customer-delete confirmation dialog displays a German warning that names the archived-project count when `archivedProjectCount > 0` (sourced from `GET /api/customers/:id`). When the count is 0, the standard confirmation text is used. Rationale: the warning prevents silent destructive data loss — deleting a customer atomically purges those archived projects (and any draft invoices on them) when the customer is deletable per the cascade rule (see [AC-91](#1511-customer-management) and [ADR-0017](../adr/0017-soft-delete-as-board-archive.md)). Customers whose project graph carries any issued or cancelled invoice are blocked separately by [AC-307](#1511-customer-management); the affordance is disabled before this dialog is reached.
- **AC-124** `[crit]`: Creating a customer with a client-supplied `id` persists the row under that id. Replaying the same request (same id, same user-supplied fields) returns the existing row with no duplicate persisted. A concurrent replay of the same id and body results in one insert and one replay, never two rows. See [api.md §14.2.5](api.md#1425-customer-management) for the field-comparison rule.
- **AC-306** `[crit]`: The `Customer` entity carries an optional `ustId` field (USt-IdNr.) ([data-model.md §5.6](data-model.md#56-customer-entity)). `POST /api/customers` accepts the field at create; `PATCH /api/customers/:id` accepts the field with the standard `null`-clears semantics; `GET /api/customers/:id` returns the field when set. The field participates in the customer idempotent-replay field comparison ([api.md §14.2.5](api.md#1425-customer-management)). The field is **not** required by the customer form regardless of mode; the requiredness gate runs at invoice issuance against `recipient.ustId` only when the draft's `taxMode = 'reverse_charge'` (per AC-289 extension). Pre-fills `Invoice.recipient.ustId` on draft creation when set.
- **AC-307** `[crit]`: `DELETE /api/customers/:id` is rejected with `409 CONFLICT` and `code = CUSTOMER_HAS_INVOICES` when any of the customer's projects (active or archived) carries at least one issued or cancelled `Invoice` row. Draft invoices do not trigger the rejection — they cascade-delete with their project on the customer's atomic-purge cascade. `details.invoiceCount` carries the count of issued + cancelled rows. The customer row, projects, and invoices are unchanged on rejection. `GET /api/customers/:id` exposes the count as `invoiceCount` (issued + cancelled only) so the destructive-warning UI ([ui/management.md §8.9.5](ui/management.md#895-delete-customer)) renders the matching disabled state. A customer whose projects (active + archived) carry zero issued or cancelled invoices behaves as before (existing AC-91 / AC-92); a customer whose archived projects carry only draft invoices is deletable, and the cascade removes those drafts alongside the projects.
- **AC-80** `[vis]`: The customer management view displays a searchable, paginated table of all customers with project counts.
- **AC-81** `[vis]`: Creating a customer makes it immediately available in project creation/editing dropdowns without page reload.
- **AC-85** `[vis]`: The critical path "create customer → create project referencing that customer" works without page reload or manual refresh.
- **AC-128** `[vis]`: The customer create form shows a dropdown of existing customers whose names case-insensitively contain the current input (substring match). Clicking a match closes the create form and opens that customer's edit form. When no matches are found, no dropdown appears. When the search request fails, no dropdown appears and no error is surfaced — the form continues to function.
- **AC-129** `[vis]`: On submit, if the entered customer name matches an existing customer's name (case-insensitive, whitespace-normalized), a confirmation dialog blocks the create until the user explicitly opts in via "Trotzdem erstellen". Cancelling returns to the form without dispatching a request.

- **AC-325** `[crit]`: Export-job completeness per the [api.md §14.2.4](api.md#1424-unified-data-exchange) "Export job — build and lifecycle" design note. A `ready` export archive covers **exactly** its own envelope's `attachments[]` — the invariant the importer enforces pre-wipe ([AC-327](#1514-data-exchange)) — established two ways:
  - **No skipping.** An attachment whose DEK unwrap, B2 fetch, or AES-256-GCM decrypt fails terminates the job `failed` with `error_detail` naming the offending attachment id; no archive is served (`GET :id/download` → `409 EXPORT_JOB_NOT_READY`, [AC-324](#1514-data-exchange)). An archive missing a row is an unrestorable backup and the operator would learn that only at restore time; the remedy for a transient fault is to re-run the export, not to ship a partial artifact labelled success. Transient storage faults are already retried inside the S3 client (SDK default: 3 attempts, standard backoff), so a fetch failure that reaches the build is a genuine unavailability.
  - **One source of truth.** The archive set is derived FROM the envelope (the withheld `originalKey` / `wrappedDek` columns are looked up by the envelope's own ids), never re-derived by a second `status='ready'` query. The envelope is read in a `repeatable read read only` snapshot that commits before the build; a second, later read would diverge from it — an upload completing mid-build would land in the archive but not the envelope, yielding a `ready` archive the importer rejects, with healthy counters and no bad row. A row that becomes `ready` after the snapshot belongs to the next export, not this one. The snapshot pins the row **set**, not the bytes: `originalKey` is read live, so a row hidden or purged after the snapshot commits fails the build under the no-skipping rule above rather than being read from its noncurrent version — loud, and the operator re-runs.

- **AC-328** `[crit]`: Import-job restore + server re-encrypt + byte-equal roundtrip + idempotency per the [api.md §14.2.4](api.md#1424-unified-data-exchange) "Import job — restore" design note. A full roundtrip — seed (with photo + binary attachments) → export job → import job — restores every attachment row at byte-equal plaintext: business data is restored via the override transaction with IDs preserved ([AC-254](#1514-data-exchange)); each attachment is re-encrypted **server-side** (fresh DEK, AES-256-GCM, DEK wrapped under the importing instance's `BINARY_AGE_RECIPIENT`, ciphertext PUT to B2, the PUT's version-id captured into `version_id` / `thumb_version_id` so the restored row hides/restores through the Papierkorb like an uploaded one) with `id` / `createdBy` / `createdAt` preserved; the plaintext recovered via `download-url` byte-equals the source ([AC-416](#1526-attachments)); photo thumbnails are regenerated server-side (separate per-blob DEK, `.thumb` key) and need NOT byte-equal the source. Re-running the job is idempotent on attachment `id` — the override wipe clears `attachments` first, so a re-run is a deterministic full replace and a post-run SELECT shows no duplicate rows. A restore that ends short of its own envelope's `attachments[]` terminates `failed`, never `ready` — the import-side mirror of the export's completeness rule ([AC-325](#1514-data-exchange)); a half-restored backup labelled success is the failure the operator discovers at the next restore. The browser is never in the byte path.

- **AC-333** `[crit]`: Jobs — realtime per the [api.md §14.2.4](api.md#1424-unified-data-exchange) "Jobs — progress + realtime" design note. Every lifecycle transition emits a `data_exchange_job_changed` SSE frame; progress emissions are throttled (a thousand-file job emits far fewer than a thousand frames). The frame is invalidation-only — it carries no data payload ([ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)); consumers refetch the job over its REST surface.
- **AC-334** `[crit]`: Jobs — staging reaper per the [api.md §14.2.4](api.md#1424-unified-data-exchange) "Jobs — staging + reaper" design note. A staged archive — a `ready` export artifact or an abandoned/terminal import upload — older than the takeout staging TTL **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)) is swept from the VPS-local staging path by the scheduled reaper. A download after the sweep returns `404 NOT_FOUND` ([AC-324](#1514-data-exchange)).
- **AC-335** `[vis]`: The Daten job UI end-to-end per [ui/daten.md §8.11.1](ui/daten.md#8111-export) + [§8.11.2](ui/daten.md#8112-import). The Export dialog drives `POST /api/export-jobs` → progress readout (files / bytes + current item) → download, renders the mobile-warning **[C]** below the configured breakpoint, and re-attaches via the mount-time resume probe after a page reload. The Import dialog drives file pick → confirmation-phrase input → resumable upload progress → server processing phases → re-authentication after the user-wipe → restored-counts summary. A picked archive always opens the confirmation gate, never a prior terminal job's summary ([ui/daten.md §8.11.2](ui/daten.md#8112-import)) — so the restore is repeatable, not a once-per-deployment action. Both dialogs drive the job endpoints rather than orchestrating bytes client-side.
- **AC-365** `[crit]`: The import job ([AC-328](#1514-data-exchange)) restores an attachment referenced by an envelope invoice's `renderedPdfBinaryDescriptorId` as a rendered invoice PDF. After an export → import roundtrip of an issued invoice, `GET /api/invoices/:id/pdf` returns byte-equal bytes, the descriptor satisfies [AC-364](#1530-invoices), and its object carries the invoice lock ([AC-296](#1530-invoices)).

### 15.17 Data Integrity

- **AC-94** `[crit]`: A concurrent state transition on the same project is rejected as a conflict (per the conflict error category in [api.md §14.4.1](api.md#1441-error-categories)). The project remains in the state produced by the first transition.
- **AC-375** `[crit]`: A versioned edit — Update customer, Update draft, Delete draft, Upsert company profile ([api.md §14.2](api.md#142-operations)) — carrying a stale `expectedVersion` is rejected with `409` `VERSION_CONFLICT`. The row is unchanged; no audit row is written and no realtime event is emitted.
- **AC-376** `[crit]`: Issue invoice carrying a stale `expectedVersion` is rejected with `409` `VERSION_CONFLICT`. The invoice stays a draft without a number, the project keeps its status, no audit row, rendered artifact or realtime event is written, and the next successful issuance receives the number the rejected call would have received.
- **AC-377** `[crit]`: A versioned edit or Issue invoice without `expectedVersion` is rejected with `422 VALIDATION_ERROR`; the row is unchanged.
- **AC-378** `[crit]`: Every committed API write to a customer, draft invoice or the company profile changes its `version` — including the issuance of a draft — so a later versioned operation carrying the prior version is rejected per AC-375. Cancelling an issued invoice leaves its `version` unchanged.
- **AC-379** `[crit]`: An edit form whose entity is changed by another session and refreshed in the background after the form opened, then saved, receives `VERSION_CONFLICT`; the UI shows the stale-write message, displays the refetched values, and does not retry ([ui/behavior.md §9.5](ui/behavior.md#95-asynchronous-mutation-behavior)).
- **AC-381** `[crit]`: Two versioned writes to one entity carrying the same current `expectedVersion`, run concurrently — including Update draft concurrent with Issue invoice — result in exactly one commit; the other writes nothing and is rejected with `VERSION_CONFLICT`, or with the state error the check order puts first ([data-model.md §6.4](data-model.md#64-concurrency) — e.g. `INVOICE_FROZEN` for an Update draft that lost to Issue invoice).
- **AC-382** `[crit]`: The `Ausstellen` and `Verwerfen` confirmation dialogs on a draft row ([ui/project-detail.md §8.15.11](ui/project-detail.md#81511-invoice)) preview the draft's recipient, lines, `taxMode`, `performanceDate` and totals. If the draft changes after the dialog opened, confirming is rejected with `VERSION_CONFLICT` — a background refresh does not advance the version the dialog sends.
- **AC-96** `[crit]`: The database rejects a project row with a `status` value outside the valid workflow states (defense-in-depth CHECK constraint).
- **AC-97** `[crit]`: The database rejects a project row where `plannedEnd < plannedStart` (defense-in-depth CHECK constraint).
- **AC-98** `[crit]`: Deleting a user nullifies the audit references (`createdBy` / `updatedBy`) on any customer records that user created or last modified.
- **AC-99** `[crit]`: Project creation (insert + worker assignment) is atomic. If worker assignment fails, the project row is not persisted.
- **AC-127** `[crit]`: A create request carrying a client-supplied `id` that already identifies a row, but whose body differs from the stored row in any participating field, is rejected with the `IDEMPOTENCY_CONFLICT` error code and the German message `"Diese Anfrage-ID wurde bereits mit abweichenden Daten verwendet."` The stored row is unchanged. Applies to both customer and project creation.
- **AC-516** `[crit]`: If a request body carries a field the operation does not define, at any depth, the system refuses it with `422 VALIDATION_ERROR` and changes nothing ([api.md §14.4.2](api.md#1442-error-principles)).
- **AC-390** `[crit]`: After `seed(db, { force: true })` completes, the database contains exactly the users enumerated in `SEED_USERS`, 21 customers, 19 projects, and 7 `project_workers` rows. Row counts are the seed's observable contract — drift breaks downstream tests and demo state. See [data-model.md §7](data-model.md#7-seed-data-specification).
- **AC-391** `[crit]`: After `seed(db, { force: true })` completes, the `users` table carries exactly the users enumerated in `SEED_USERS` — usernames and `active` flags match the constant, and `SEED_DEFAULT_PASSWORD` verifies against every stored `passwordHash`. (`SEED_USERS` and `SEED_DEFAULT_PASSWORD` are test-layer assumption constants pinning seed-produced values.) See [data-model.md §7](data-model.md#7-seed-data-specification).
- **AC-392** `[crit]`: After `seed(db, { force: true })` completes, every project `number` carries the year prefix matching the calendar year at seed time. See [data-model.md §7](data-model.md#7-seed-data-specification).
- **AC-164** `[crit]`: A malformed users fixture (missing required field, wrong type) causes the seed loader to throw a typed validation error before any row is inserted. No partial state lands in `users`. Rationale: silent partial seed corrupts dev and test state class-wide; fail-fast is the data-integrity posture.

### 15.19a Brand Logo

- **AC-360** `[crit]`: `BRANDING.mark.logo` names an optional asset path, resolved against the static root the browser is served from. Resolution refuses, returning no asset, when the path is not an absolute same-origin one — the identical string is the browser's image source, so a relative or protocol-relative path would feed the two surfaces different bytes — when it does not name a file under that root's `brand/` directory (including a `..` traversal that resolves out of it), when the file's leading bytes are neither a PNG signature nor a JPEG SOI marker, when the file exceeds the 2 MB cap, or when it cannot be read. The format is sniffed from the bytes, never trusted from the extension. A file that is present but unusable is a refusal, not a reason to search a different root — embedding bytes other than the ones the browser loads would defeat the single-asset contract. Every refusal yields no asset rather than throwing: resolution runs inside the invoice-issuance transaction while it holds the gapless number-sequence row lock ([AC-286](#1530-invoices)), so a branding misconfiguration must never be able to abort an issuance.
- **AC-361** `[vis]`: With `BRANDING.mark.logo` unset, the header renders the generic mark painted from `BRANDING.mark.bg` / `.bars`, shown only at the narrow widths where the wordmark is hidden. With it set, the header renders the configured asset at every viewport width. The mark is decorative in both cases (`alt=""`, `aria-hidden`) — the accessible name comes from the enclosing navigation control. A configured asset that fails to load falls back to the generic mark, so a per-deployment path typo degrades rather than leaving a broken image on every page.
- **AC-362** `[crit]`: A rendered invoice embeds the configured logo as an image XObject in the issuer block, scaled to fit its box preserving aspect ratio and never enlarged past its natural size. With no logo configured, with one configured but unresolvable under AC-360, or with one whose bytes the document engine cannot decode, the invoice renders with no image and issuance completes normally — a branding asset is never able to fail an issuance, at either stage. The rules bracketing the line-item table are painted in `company_profile.accentColor` when set and `BRANDING.accent.light` otherwise; a malformed accent value falls back rather than throwing. The light variant is the correct default regardless of the reader's theme — the sheet is white.

### 15.19b App Shell Identity

- **AC-363** `[infra]`: The installation's name and its shell colors have one definition site each, in the branding configuration. `BRANDING.appName` is the served document's `<title>`, the PWA manifest's `name`, and the Service Worker's fallback notification title; `BRANDING.shortName` is the manifest's `short_name`; `BRANDING.shell.themeColor` is both the served document's `theme-color` meta and the manifest's `theme_color`; `BRANDING.shell.backgroundColor` is the manifest's `background_color`. It declares the installability fields and a maskable icon purpose, and every icon path it names resolves to a file that ships. The icon files are outside this boundary: they are square marks a deployment replaces wholesale, and they hold their own copies of the mark colors.

### 15.21 Role Scoping

These criteria pin the per-role read surface described in [index.md §4.2](index.md#42-users) and [api.md §14.3](api.md#143-authorization-rules). They describe behavior, not mechanism — the implementation may realize scoping via a query filter, a repository-layer predicate, or any equivalent approach, as long as the observable contract holds.

- **AC-145** `[crit]`: A worker's `GET /api/projects` returns only projects where the caller is recorded in `project_workers`. A worker assigned to no project receives an empty list. Owner and office receive every non-deleted project (unchanged). Verified by API integration tests using seed users with deterministic assignments.
- **AC-146** `[crit]`: A worker's `GET /api/customers` returns only customers referenced by at least one project where the caller is recorded in `project_workers`. A customer reachable to the worker exclusively through a soft-deleted project is excluded. Owner and office receive every customer (unchanged) — the soft-delete status of a customer's linked projects does not restrict the owner/office customer list, which is the parity clause to AC-145's "every non-deleted project (unchanged)".
- **AC-147** `[crit]`: A worker's `GET /api/projects/:id` succeeds only when the caller is recorded in `project_workers` for that project; otherwise the request is rejected with an authorization error (`NOT_PERMITTED`). The server must not respond with `NOT_FOUND` for a project that exists but the worker is not assigned to — the two outcomes are distinguishable to the caller. This is acceptable under the project's threat model: callers are internal, authenticated users and project IDs are UUIDs that are not enumerable from outside, so resource existence is not a secret at the role boundary (compare with [api.md §14.4.1](api.md#1441-error-categories)'s `NOT_PERMITTED` vs `NOT_FOUND` distinction). Owner and office are unaffected.
- **AC-148** `[crit]`: A worker's `GET /api/customers/:id` succeeds only when the customer is referenced by at least one project where the caller is recorded in `project_workers`; otherwise the request is rejected with an authorization error (`NOT_PERMITTED`). Owner and office are unaffected.
- **AC-149** `[vis]`: A manual URL entry to a path the caller's role is not permitted to access (for example, a worker navigating to `/kunden`) presents an explicit not-permitted error surface in the client: a visible error message indicating the access is denied, no redirect to another view, and the URL in the address bar remains unchanged. This error surface is distinct in presentation from an API 403 returned mid-interaction (see [ui/behavior.md §9.5](ui/behavior.md#95-asynchronous-mutation-behavior)); this criterion covers the route-entry case. Coverage spans every role × every path not permitted for that role under the matrix in [AC-75](#1515-navigation).
- **AC-150** `[vis]`: The Export and Import controls inside the Daten view are rendered only when the caller holds the corresponding permission — Export ([ui/daten.md §8.11.1](ui/daten.md#8111-export)) requires `data:export`; Import ([ui/daten.md §8.11.2](ui/daten.md#8112-import)) requires `data:restore`. This is defense-in-depth against the nav-level gate in [AC-142](#1514-data-exchange): even if the Daten route becomes reachable without the permission (e.g. a bug in the nav gate, a manual URL probe, a client build drift), the component itself must not present the action to a caller who cannot use it. The server remains authoritative ([AC-133](#1514-data-exchange) for export, [AC-134](#1514-data-exchange) for import).
- **AC-121** `[crit]`: Any UI control that triggers a mutation requiring a permission the current user lacks is hidden, not rendered and server-rejected. Covers action buttons (create, delete, save, transition, forward) and auto-save inputs (date fields) across the kanban board, management views (projects, customers, users), and the project detail panel. Rationale: rendering an affordance that always 403s is misleading state — the user cannot know in advance which of their actions will succeed.

### 15.22 Backup and Recovery

These criteria pin the Layer 2 backup-and-drill cycle ([architecture.md §11.10](architecture.md#1110-full-state-backup-layer-2), [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md)). Status fields referenced below are defined in [data-model.md §5.9](data-model.md#59-backup-status-entity).

- **AC-165** `[crit]`: A backup run whose Tier 1 verify-on-create produces a per-table manifest that does not equal the source manifest fails the run. No artifact is uploaded to the off-site object store; `meta_backup_status.lastBackupOk` is `false` and `lastBackupError` identifies the failing table.
- **AC-166** `[crit]`: A backup run whose Tier 1 verify-on-create matches the source manifest uploads the encrypted dump artifact and its encrypted manifest sidecar to the off-site object store; `meta_backup_status.lastBackupOk` is `true` and `lastBackupAt` equals the run timestamp.
- **AC-167** `[crit]`: No backup artifact written to the off-site object store is readable without the operator's private decryption material. Both the dump and the manifest sidecar are encrypted before upload; a run that cannot produce an encrypted artifact fails and uploads no artifact. Tool choice lives in [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md).
- **AC-168** `[crit]`: When the operator's private identity is absent from tmpfs, the Tier 2 verify-on-cycle drill is skipped. `meta_backup_status.lastDrillAt` is not advanced and `lastDrillOk` is not coerced from its prior value. A skipped drill is not reported as a failure.
- **AC-169** `[crit]`: Every write to `meta_backup_status` — a backup run of any outcome, or a drill that is not skipped (AC-168) — is followed by a write of the status mirror object to the off-site object store with the same `lastBackupAt`, `lastBackupOk`, `lastBackupError`, `lastDrillAt`, `lastDrillOk`, `lastDrillError`, and `updatedAt` values, except that the mirror's error fields carry only the failure stage, not the error detail — the mirror is unencrypted and detail can quote stored data. A skipped drill writes neither. If the mirror-object write fails, the failure is appended to the writing cycle's error field (`lastBackupError` or `lastDrillError`), preserving its existing content; `lastBackupOk` and `lastDrillOk` are unchanged and this follow-up row write is not mirrored. Encrypted artifacts already uploaded remain in place under the bucket's immutability window and are subject to the normal retention lifecycle.
- **AC-170** `[vis]`: On every authenticated surface the backup-freshness badge is visible only to callers with role `owner`. Other authenticated roles and the unauthenticated login screen do not render the badge. The badge renders as a fixed-size icon at every state; colour (green / amber / red / muted-unknown) is the only signal of severity, so layout does not shift between readings. When the `meta_backup_status` row carries `lastBackupAt`, the tooltip and tap toast append the run timestamp formatted in German (`HH:mm EEE dd.MM.yyyy`) so the operator can tell when the reading was earned. The `unknown` and `backup-never-run` states omit the timestamp — no run to point at.
- **AC-171** `[crit]`: When the status source is unreachable (DB down or the status mirror object not retrievable), the backup-freshness badge renders an explicit "Status unbekannt" state. When `lastDrillAt` is absent (no Tier 2 drill has ever succeeded or failed), the badge renders as drill-stale at the red threshold. The badge is not silently hidden and no stale-but-green state is shown. Rationale: misleading state is a critical defect class per [ADR-0014](../adr/0014-ac-tier-system-critical-vs-design.md).
- **AC-172** `[infra]`: The `backup` compose service is defined in the compose file with the configured interval **[C]** expressed in cron form, and starts with the rest of the stack. Verified by compose-file review — the tier reflects that the observable is the source tree, not a runtime check.
- **AC-173** `[infra]`: The backup bucket has object-lock retention AND a lifecycle rule, both configured per the canonical values in [ADR-0020 §Retention](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md#retention). Verified by infrastructure review against the runbook; direct automated assertion against the provider is not required. Provider and bucket name live in [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md) and the runbook.
- **AC-174** `[crit]`: The per-table content checksum is deterministic across runs on identical data. Two backup runs against the same database state produce byte-equal manifest values for every table. Rationale: non-deterministic checksums invalidate Tier 1 and Tier 2 comparison.
- **AC-175** `[infra]`: The operator's private decryption identity is never persisted to disk on the VPS. The drill-key load path writes the identity only into a tmpfs mount; a reboot removes it. Verified by the runbook procedure and by repository-level review of the drill-key load script. Tool choice and script name live in [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md).
- **AC-176** `[crit]`: The owner's backup-freshness badge reads `BackupStatus` from the authenticated `GET /api/auth/me` response (`backupStatus` field, owner-only — see [api.md §14.2.1](api.md#1421-authentication)). When the status row is unreachable the field is omitted, which the client maps to the explicit "Status unbekannt" state per AC-171; a silently-empty surface is forbidden. No public `/api/backup/status` endpoint is exposed — the badge has no unauthenticated consumer.
- **AC-344** `[crit]`: The source manifest and the dump artifact are produced from a single database snapshot. A run that overlaps concurrent committed writes still passes Tier 1 — the manifest recomputed from the restored dump equals the source manifest — and uploads per AC-166. A run that cannot establish the shared snapshot fails and uploads no artifact; falling back to an independently-snapshotted dump is forbidden. Rationale: a Tier 1 mismatch is the corruption signal (AC-165), and a mismatch caused only by concurrent writes makes that signal unreadable while discarding a sound backup. Mechanism in [ADR-0020 §Manifest and dump share one snapshot](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md#snapshot).
- **AC-345** `[crit]`: Every wait a backup or drill run performs is bounded — subprocesses, off-host requests, and database statements alike. External processes it starts carry a wall-clock limit and are terminated on exceeding it. Requests to the off-site object store carry a wall-clock limit and abort on exceeding it. Every database statement it issues carries a lock-wait limit, and the manifest transaction additionally carries an overall statement limit. Exceeding any bound fails the run, and the status row records the reason — not merely the operation that failed. One exemption: the verify database instance, which is long-lived by design and stopped by the run that started it. Rationale: the scheduler runs one tick at a time, so a single unbounded wait suppresses every later run and reports nothing — the backup stops happening with the status surface still green on its last success. The bound on the status write itself is what keeps that reporting possible when the blocked resource is the status table.
- **AC-346** `[crit]`: A run that feeds a subprocess through stdin survives that subprocess exiting before it has consumed the input — the run fails with the failure recorded on the status row, and the runner process does not terminate. Rationale: the backup runner is a separate entrypoint with no uncaught-exception guard, so an unhandled pipe error ends the process before the status write. The run then reports nothing at all and the freshness badge holds its last success, which is the misleading-state class [ADR-0014](../adr/0014-ac-tier-system-critical-vs-design.md) rules out. Reachable on ordinary failure paths, not exotic ones: `age` on a malformed recipient, `pg_restore` on a corrupt archive.
- **AC-366** `[crit]`: A backup run against a source database without page checksums fails before producing an artifact. No artifact is uploaded, `meta_backup_status.lastBackupOk` is `false`, and `lastBackupError` names the missing checksums. Rationale: without page checksums, corruption in stored rows reads back silently — the dump carries it and Tier 1 compares against a manifest read from the same pages, so every run passes while clean backups age out of retention.
- **AC-368** `[infra]`: The Layer 2 disaster-recovery procedure, before the application serves again, runs the binary recovery tool ([AC-441](#1526-attachments)) with a cutoff before the backup snapshot by one hour plus the attachment orphan-reaper TTL **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)) — an object is written before its row commits, and a row still `pending` in the dump is reaped after the restore, then advances each `invoice_sequence` `(year, kind)` past the highest invoice number in the tool's index — recovered and failed versions alike. If any invoice-PDF version since the cutoff carries no readable number, every `(year, kind)` from the cutoff's year onward instead advances by the count of invoice-PDF versions since the cutoff. Failed versions are recorded in the incident record; they do not block serving. A gap is acceptable, a reissued number is not ([data-model.md §6.13](data-model.md#613-gapless-sequence-allocation)). Verified by runbook review.
- **AC-370** `[crit]`: A backup run writes only the backup fields of `meta_backup_status` (`lastBackupAt`, `lastBackupOk`, `lastBackupError`) and a drill only the drill fields (`lastDrillAt`, `lastDrillOk`, `lastDrillError`), plus `updatedAt`; neither changes the other's. Rationale: the drill follows every backup, so a shared error field lets either cycle's outcome erase the other's failure cue.

### 15.23 Audit Log

These criteria pin the single-write-path audit surface ([ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md), [data-model.md §5.10](data-model.md#510-audit-log-entity), [api.md §14.2.8](api.md#1428-audit-log), [ui/workflow-views.md §8.4.1](ui/workflow-views.md#841-activity-feed), [ui/management.md §8.13](ui/management.md#813-audit-view)).

- **AC-177** `[crit]`: Every mutation on an audited entity (any `AuditEntityType` value — see [data-model.md §5.10](data-model.md#510-audit-log-entity)), **except the non-audited self-preference writes documented in [data-model.md §5.10](data-model.md#510-audit-log-entity) "Non-audited self-preference writes on `UserAccount`"**, produces exactly one `audit_log` row written in the same database transaction as the domain-state change. A domain-state change without its audit row is not possible (save the carve-out); an audit row without its state change is not possible. Row carries a non-null `actorId` AND `actorKind = 'user'` when an authenticated caller drove the mutation; a non-null `actorReason` AND `actorKind = 'system'` and null `actorId` when the write originates from an unattended path. Concurrent mutations on the same entity produce serialized audit rows whose order matches the committed state-change order. Each audit row's `payload.before` reflects the row state read inside the mutation's own transaction before the write.
- **AC-178** `[crit]`: The first-run admin bootstrap ([ADR-0010](../adr/0010-first-run-admin-bootstrap.md)) writes an `audit_log` row with `actorKind = 'system'`, null `actorId`, a non-empty `actorReason` (e.g., `"first-run-bootstrap"`), `entityType = 'user'`, and `action = 'create'`. The database's CHECK constraint rejects a system entry whose `actorReason` is null or empty. Rationale: without a non-empty reason, the bootstrap mutation is invisible in the activity feed, leaving the first administrator's creation unaccounted for.
- **AC-179** `[infra]`: A CI-enforced static architecture check fails the build when an audited-table mutation (insert, update, or delete on any audited table) is authored outside the service-layer's single-write-path helper ([ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)). The check's audited-table set is the `AuditEntityType`-derived set from [data-model.md §5.10](data-model.md#510-audit-log-entity) — `attachment` is a full member of `AuditEntityType`, so the `attachment` table is wired into the check through the same derivation as every other audited table (no carve-out entry, no hand-maintained append). A new `AuditEntityType` value whose corresponding table is not wired into the check fails CI. `audit_log` itself is not in the audited set: `mutate()` is its legitimate writer, and its integrity is guaranteed by the append-only invariant ([§5.10](data-model.md#510-audit-log-entity)) plus the retention-cleanup allowlist. The check allowlists migrations, the unified restore path ([api.md §14.2.4](api.md#1424-unified-data-exchange)), business-data seed loaders, the retention cleanup job ([data-model.md §6.10](data-model.md#610-audit-log-retention)), the attachment init `pending`-row insert (state-machine pre-step, no audit row — [AC-407](#1526-attachments)), and the attachment orphan-reaper ([AC-408](#1526-attachments)). Each allowlist addition is a reviewed line in the check's configuration.
- **AC-180** `[crit]`: `GET /api/audit` requires `audit:read` — owner and office under the default role set. Worker and bookkeeper receive `403 NOT_PERMITTED`. The surface has no reachability narrowing: both roles that hold `audit:read` are unscoped for entity reachability (only the destructive-action narrowing below applies, and that narrows office).
- **AC-182** `[crit]`: An `audit_log` entry whose `action` is `purge` (any entity type), `delete` on `entityType = 'user'`, or `update` on `entityType = 'user'` where the payload diff touches `roles`, is returned by `GET /api/audit` only to callers whose destructive-action scope admits them — owner under the default role set (see [api.md §14.2.8](api.md#1428-audit-log)). For office the destructive-action scope excludes these entries from list and get-by-id responses alike. Permissions remain coarse — `audit:read` admits the caller to the surface; the destructive-action narrowing is orthogonal (parallel to the worker-scope pattern in [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md)).
- **AC-183** `[crit]`: A subscriber of the post-commit notification publisher that throws an unhandled exception does not roll back the originating mutation. The domain-state change and the `audit_log` row are committed; the publisher emits a structured operational log line with fields `event = 'audit-publisher-handler-error'`, `audit_entry_id` (the committed row's id), and `error_message`. Rationale: coupling subscriber correctness to domain transactionality would make third-party or future integrations a single point of failure for every mutation.
- **AC-184** `[crit]`: A scheduled cleanup job removes `audit_log` entries older than the configured retention window **[C]** (90 days default, see [architecture.md §12.2](architecture.md#122-company-configurable-settings)). Each run emits exactly one structured operational log line at `info` level with fields `event = 'audit-retention-cleanup'`, `window_days` (integer — the applied retention window), `removed_count` (non-negative integer; `0` on a no-op run), and `ran_at` (ISO 8601 run timestamp). Operators verify retention by querying the operational log for `event = 'audit-retention-cleanup'`; the Aktivität UI does not surface retention events. No `audit_log` row is produced by the cleanup job itself (scope is domain entities only — [data-model.md §5.10](data-model.md#510-audit-log-entity), [§6.10](data-model.md#610-audit-log-retention)).
- **AC-185** `[vis]`: Both activity surfaces — the project detail panel's activity feed and the global Aktivität view ([ui/management.md §8.13](ui/management.md#813-audit-view)) — render `audit_log` entries in reverse-chronological order (newest first, `id` as stable tiebreaker) and display `"Keine Aktivität"` when the result set is empty. The per-project feed paginates via `"Ältere anzeigen"` (older entries append without collapsing the current set); the global view paginates at the configurable list page size **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)) and AND-composes its filter bar (entity type, entity, actor, date range, action) with a client-side block on `to < from`. The global view's `Projekt` column ([AC-342](#1532-activity-dock)) is read-only — it is rendered, not filterable; users wanting a project-narrowed feed select `entityType = 'project'` plus the existing `entityLabelQuery`.
- **AC-186** `[vis]`: The payload drawer (`Details anzeigen`) is rendered on a feed entry only when the API response for that entry includes a non-null `payload`. Owner and office receive a payload on every entry; the drawer therefore renders on every feed row with a non-empty diff and expands inline without a route change.
- **AC-187** `[crit]`: The owner sees destructive-action entries (`purge`, `delete` on user, role-change updates) in the global Aktivität view — destructive-action scope admits owner with no filter. Office is the only other role that holds `audit:read` under the default matrix; the same scope excludes office from these entries. Verified by listing and get-by-id against the audit endpoint. (The per-project detail-panel feed filters on `{ancestorType: 'project', ancestorId}` ([architecture.md §11.12](architecture.md#1112-audit-ancestor-link)); of the destructive set only `purge` has a project ancestor, and a purged project leaves no openable detail panel — so the per-project surface has no observable destructive-visibility contract to pin.)
- **AC-188** `[crit]`: `audit_log.entityLabel` is a point-in-time snapshot captured at write time. Mutations on the target entity do not update prior audit rows' `entityLabel`: a rename writes a new row carrying the new label while prior rows keep the old one, and a delete/purge leaves prior rows' labels intact. Rationale: the activity feed must remain readable after renames or purges; a read-time JOIN or a back-fill would rewrite history — the exact misleading-state failure mode `entityLabel` exists to prevent ([data-model.md §5.10](data-model.md#510-audit-log-entity) "Entity label snapshot").

### 15.28 Realtime Events

Criteria for the SSE invalidation channel ([api.md §14.2.13](api.md#14213-realtime-events), [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)).

- **AC-268** `[crit]`: `GET /api/events` accepted by the existing session middleware returns `200 OK` with `Content-Type: text/event-stream` and an open response stream that does not close on its own. An unauthenticated request returns `401 UNAUTHENTICATED` / `SESSION_EXPIRED` and no stream begins. The response carries no `Cache-Control` directive (the protocol is non-cacheable per the WHATWG SSE spec). A subscribed connection receives every event the server broadcasts over the lifetime of the connection — verified by emitting a synthetic `storage_usage_changed` and asserting the connected client observes the event frame.
- **AC-269** `[crit]`: A connection held idle for the configured heartbeat window observes a heartbeat comment line (`:` keepalive) within 25 seconds — the interval is configurable **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings); default 25 seconds). When the server closes the connection, the client's browser-native `EventSource` reconnects with its own backoff and resumes receiving subsequent broadcasts; no `Last-Event-ID` replay is performed (events are invalidation hints, not a log — [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)).
- **AC-270** `[crit]`: Each of the three AttachmentService mutation paths (`completeUpload` for `pending → ready`, `hide` for `ready → hidden`, `restore` for `hidden → ready`), the hidden reaper (`attachment-hidden-reaper` per [AC-426](#1526-attachments)), the project-purge cascade (`DELETE /api/projects/:id/purge` per [AC-502](#1512-projects) when the purged project carried at least one `attachment` row contributing non-zero bytes — i.e. a `ready` or `hidden` row), and the customer-delete cascade (`DELETE /api/customers/:id` per [AC-91](#1511-customer-management) when at least one of the atomically purged archived projects carried such a row) emits exactly one `storage_usage_changed` event post-commit that reaches a subscribed `/api/events` connection. A purge / customer-delete whose cascade removes no byte-bearing rows (purged project had no attachments or only `pending` rows; customer had no archived projects, or all archived projects were empty) emits zero events — pending rows contribute zero on every counter so the global figure does not move. The orphan reaper ([AC-408](#1526-attachments)) deletes only `pending` rows and emits zero events for the same reason. Emission is post-commit — a mutation that aborts inside the transaction emits no event ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)); a customer-delete that throws inside its single enclosing transaction emits nothing even when the throw lands after the per-project purge writes (those writes roll back with the transaction). A subscriber whose write fails (closed socket, slow consumer) does not affect the dispatch to other subscribers — the failure is logged and the offending subscriber is removed; the originating mutation has already committed and is unaffected ([§11.11](architecture.md#1111-notification-publisher-and-dispatch) parity).
- **AC-275** `[crit]`: A held `/api/events` stream observes a server-initiated end and is removed from the bus's subscriber set within one heartbeat interval after the underlying session becomes invalid. The check covers all four invalidation paths uniformly: natural expiry (`session.expiresAt < now`), logout / reaper deletion of the session row, and admin lockout (`users.active = false`). Each path is verified by an integration test that opens a stream, mutates the session or user state directly, and asserts the bus subscriber count drops within the budget. DB re-validation cadence is independent of broadcast rate — a test with N concurrent connections + M broadcasts per minute produces O(N) re-validation queries per heartbeat, not O(N·M). Transient DB errors during re-validation skip the tick rather than disconnecting the subscriber. Bug history: [CWE-613](https://cwe.mitre.org/data/definitions/613.html) — without re-validation a logged-out, expired, or deactivated user's tab keeps receiving frames until the client itself disconnects; a payload-bearing event would leak.
- **AC-276** `[crit]`: Each of the ten project-mutation sites (`ProjectCrudService.createProject`, `ProjectCrudService.updateProject` — including the assigned-worker-only path that writes only `project_workers`, `ProjectCrudService.deleteProject` for soft-delete / archive, `ProjectCrudService.restoreProject` for un-archive, `ProjectCrudService.purgeProject` for the hard delete in [AC-502](#1512-projects), `ProjectTransitionService.transitionForward` per [AC-458](#151-workflow-board), `ProjectTransitionService.transitionBackward` per [AC-458](#151-workflow-board), `ProjectDatesService.updateDates` per [AC-7](#151-workflow-board), the `CustomerService.deleteCustomer` cascade per [AC-91](#1511-customer-management) when at least one archived project exists under the customer, and the `ImportService.import` paths ([api.md §14.2.4](api.md#1424-unified-data-exchange)) — both the override branch (TRUNCATE + re-insert into a non-empty target) and the empty-target branch (insert into empty tables) — on a successful commit) emits exactly one `project_changed` event post-commit that reaches a subscribed `/api/events` connection. A `CustomerService.deleteCustomer` whose target carries zero archived projects emits zero `project_changed` events — the project rows visible to subscribers are unchanged. Failure-isolation, post-commit, and tx-abort posture mirror [AC-270](#1528-realtime-events) for `storage_usage_changed` — emission is post-commit only, a mutation that aborts inside the transaction emits no event, and a subscriber whose write fails does not affect the dispatch to others or the originating mutation. For paths that may co-emit `storage_usage_changed` (`ProjectCrudService.purgeProject`, `CustomerService.deleteCustomer`), the two events' emit gates are independent — `project_changed` fires whenever the project row(s) change, regardless of whether the cascade also moved byte-bearing attachment rows.
- **AC-277** `[crit]`: Multi-user invalidation — two actors on the same install: an office session (the always-open observer) and a one-shot owner-authenticated request context driving every mutation from a session distinct from the office observer. The owner advances a project (`+1` transition per [AC-458](#151-workflow-board)), archives a project ([AC-497](#1512-projects)), restores an archived project, edits a project's planned dates ([AC-7](#151-workflow-board)), edits an assigned-worker set, and creates a new project ([AC-475](#1512-projects)). No worker actor: workers do not hold `project:transition`, `project:create`, `project:update`, `project:delete`, or `project:dates` per the role table in [api.md §14.3](api.md#143-authorization-rules), so none of the [AC-276](#1528-realtime-events) project-mutation sites are worker-reachable; contrast with storage usage, where workers DO hold `attachment:write` / `attachment:hide` ([api.md §14.3](api.md#143-authorization-rules)) and a worker arm carries weight. After each mutation the office session's project-list surfaces ([ui/management.md §8.8](ui/management.md#88-project-management-view), [ui/workflow-views.md §8.2](ui/workflow-views.md#82-kanban-view), [ui/workflow-views.md §8.3](ui/workflow-views.md#83-calendar-view)) and any open project-detail surface ([ui/workflow-views.md §8.4](ui/workflow-views.md#84-project-detail-panel), [ui/project-detail.md §8.15](ui/project-detail.md#815-project-detail-page)) reflect the change within 2 seconds of mutation commit, with no manual refresh on the office session, driven by the `project_changed` event over `/api/events` ([api.md §14.2.13](api.md#14213-realtime-events)) and the project store's SSE refresh trigger that re-issues the project reads. This is the value test the realtime channel exists to deliver for project lifecycle — the always-open-observer gap that mount + `visibilitychange` + post-mutation refresh alone leave open ([ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)), parity with [AC-450](#1529-storage-usage) for storage usage.
- **AC-320** `[crit]`: Every committed `audit_log` row emits exactly one `audit_changed` event post-commit that reaches a subscribed `/api/events` connection, via the notification publisher's `onAuditCommitted` hook ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)) — covering every audited mutation through the single-write-path helper without a per-call-site emitter. A transaction that rolls back commits no audit row and emits no event. The `data:` payload is the contentless invalidation envelope `{ "type": "audit_changed" }`; no audit content rides the channel — consumers refetch the `audit:read`-gated [api.md §14.2.8](api.md#1428-audit-log). Failure-isolation and post-commit posture mirror [AC-270](#1528-realtime-events): a subscriber whose write fails is removed without affecting other subscribers or the originating mutation.

- **AC-336** `[crit]`: Each attachment mutation that changes a project's attachment list — `AttachmentService.completeUpload` (`pending → ready`), `AttachmentService.hideAttachment` (`ready → hidden`), `AttachmentService.restoreAttachment` (`hidden → ready`), and the `attachment-hidden-reaper` (one frame per purged `hidden` row) — emits exactly one `attachment_changed` event post-commit that reaches a subscribed `/api/events` connection, co-emitted with the `storage_usage_changed` event each site already fires ([AC-270](#1528-realtime-events)). `init` (pending-row creation) emits no `attachment_changed`: a `pending` row is invisible to the gallery and the Papierkorb, so emission would be a wasted refetch (parity with AC-270's `init` exclusion). The `data:` payload is the contentless envelope `{ "type": "attachment_changed" }`. Emission is post-commit and failure-isolated on the same bus hook as [AC-270](#1528-realtime-events) — a tx that aborts emits nothing; a subscriber whose write fails is removed without affecting the originating mutation. Closes the gallery cross-user view-sync gap (issue #237).

- **AC-337** `[crit]`: Multi-user invalidation — two actors on the same install: an owner / office session (the always-open observer) parked on a project-detail page ([ui/project-detail.md §8.15](ui/project-detail.md#815-project-detail-page)) with the photo gallery / binary list and the Papierkorb (§8.15.10) open, and a one-shot session distinct from the observer driving each mutation. The actor uploads a photo (`pending → ready`), hides an attachment, and restores a hidden attachment (Papierkorb restore is owner / office only per the matrix in [api.md §14.3](api.md#143-authorization-rules)). After each mutation the observer's gallery / binary list and open Papierkorb reflect the change within 2 seconds of commit, with no manual refresh, driven by the `attachment_changed` event over `/api/events` ([api.md §14.2.13](api.md#14213-realtime-events), [AC-336](#1528-realtime-events)) and `attachmentStore`'s SSE refresh trigger that refetches the per-project attachment list(s) ([AC-409](#1526-attachments)). This is the value test the realtime channel exists to deliver for attachments — the always-open-observer gap that `attachmentStore`'s mount-only fetch otherwise leaves open ([ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)); parity with [AC-450](#1529-storage-usage) and [AC-277](#1528-realtime-events).

- **AC-338** `[crit]`: Every member of the `SseEventName` catalog union (`src/config/sseEvents.ts`, enumerated at runtime by `SSE_EVENT_NAMES`) has ≥1 registered client subscriber — an `onSseEvent(<event>, …)` call under `src/state/` or `src/ui/`. A repo scan refuses any catalog event emitted but never consumed, with an explicit allowlist (each entry carrying a non-empty `reason`) for a deliberately server-only event. Rationale: the emit side is enumerated and pinned ([AC-270](#1528-realtime-events) / [AC-276](#1528-realtime-events) / [AC-320](#1528-realtime-events) / [AC-336](#1528-realtime-events)) but the subscribe side was not — an event could ship emit-only and fire into the void, leaving the observer stale (the gallery gap, issue #237). The guard makes a new emit-only event a build failure, not a silent dead surface.

### 15.30 Invoices

Criteria for the invoice domain ([data-model.md §5.15](data-model.md#515-invoice-entity), [data-model.md §5.16](data-model.md#516-invoice-sequence-entity), [api.md §14.2.14](api.md#14214-invoice-operations), [architecture.md §11.14](architecture.md#1114-invoice-domain), [ADR-0026](../adr/0026-invoices-immutability-and-zugferd.md)).

- **AC-285** `[crit]`: `POST /api/invoices` creates exactly one `Invoice` row with `status = 'draft'`, `number` null, `issueDate` null, `renderedPdfBinaryDescriptorId` null. The row's `projectId` is FK-bound to the supplied project; `taxMode` defaults to the live `company_profile.defaultTaxMode` when not supplied; `recipient` is pre-filled from the project's customer when not supplied. The endpoint requires `invoice:write`; callers without it receive `403 NOT_PERMITTED`. A draft on an archived project is rejected with `404 NOT_FOUND` (mirrors [AC-499](#1512-projects)). The mutation produces one `audit_log` row via `mutate()` with `entityType = 'invoice'`, `action = 'create'`, ancestor `('project', projectId)` per [AC-177](#1523-audit-log).
- **AC-286** `[crit]`: `PATCH /api/invoices/:id` on a `status = 'draft'` row updates the specified fields (PATCH semantics — omitted fields unchanged); `totals` is re-derived server-side on every successful PATCH from `lines` + `taxMode`. `PATCH` on a row whose `status` is `'issued'` or `'cancelled'` is rejected with `422 VALIDATION_ERROR` and `code = INVOICE_FROZEN`; no field is mutated, no audit row is written. `DELETE /api/invoices/:id` on a `status = 'draft'` row hard-deletes the row; on a non-draft row it is rejected with `INVOICE_FROZEN`. - **AC-287** `[crit]`: `POST /api/invoices/:id/issue` runs the issuance transaction ([architecture.md §11.14](architecture.md#1114-invoice-domain)) inside one DB transaction: allocates `number` from `invoice_sequence` via an atomic `INSERT … ON CONFLICT … DO UPDATE … RETURNING next_value` on `(year, 'invoice')` (row-exclusive lock equivalent to `SELECT FOR UPDATE`), snapshots `issuer` / `recipient` / `lines` / `taxMode` / `profile` onto the row, computes `totals` server-side, renders the PDF/A-3 + factur-x.xml, writes the binary descriptor, flips the parent project's `status` to `abgerechnet`, writes exactly one `audit_log` row with `action = 'invoice:issue'`, and commits. A failure at any step rolls back the entire transaction — the sequence increment never persists (gapless property), no binary is left orphaned, the project status stays at `rechnung_faellig`, and the draft remains editable. Post-commit, exactly one `invoice_changed` SSE event AND one `project_changed` SSE event reach subscribed `/api/events` connections (the project status changed, so both consumer surfaces must invalidate). Requires `invoice:write`.
- **AC-288** `[crit]`: Two concurrent issue calls on two distinct drafts within the same calendar year produce two invoices with sequential, gapless `number` values from the `(year, 'invoice')` sequence — never duplicates, never gaps. An issue call whose transaction rolls back after sequence allocation (render failure, binary write failure, project-status flip failure) returns the value to the sequence: a subsequent successful issue allocates the same value. Verified by an integration test driving the rollback path and asserting the next successful issue receives the rolled-back value.

Delete, Restore, Complete, and Get download URL on its descriptor id return `404 NOT_FOUND` and change nothing — the row keeps its `status`, no audit row is written, the object is not hidden. Bulk fetch including its id is rejected `422 VALIDATION_ERROR`. `GET /api/invoices/:id/pdf` still returns the bytes.
- **AC-384** `[crit]`: `POST /api/invoices` and `PATCH /api/invoices/:id` store every line with `lineTotal = quantity × unitPrice`, computed on the decimal values and rounded half away from zero to 2 decimals ([data-model.md §5.15](data-model.md#515-invoice-entity)); a client-supplied `lineTotal` is rejected per AC-516. A write whose derived `lineTotal` or `totals` amount is not a finite number, or with a line `unitPrice` of more than 4 decimals, or that leaves the draft with a line whose `taxRate` is not a §5.15 rate for the draft's `taxMode`, is rejected with `422 VALIDATION_ERROR`. The rendered PDF and `factur-x.xml` carry each line's `quantity` and `unitPrice` without rounding (XML sign per [data-model.md §5.15](data-model.md#515-invoice-entity)). Issue never freezes a line without a positive `quantity`, a finite `unitPrice` and a §5.15 `taxRate` for the draft's `taxMode`, a line that breaks the equality or the 4-decimal limit, nor totals that are not finite: `POST /api/invoices/:id/issue` on such a draft is rejected with `422 VALIDATION_ERROR`: no number is allocated, the draft is unchanged, no `audit_log` row and no SSE event.
- **AC-513** `[crit]`: If a user edits, deletes, issues or cancels an invoice of an archived project, the system refuses it as not found ([api.md §14.4.1](api.md#1441-error-categories)) and changes nothing.
- **AC-514** `[vis]`: While an invoice's project is archived, the invoice list and the invoice viewer ([ui/invoices.md §8.16](ui/invoices.md#816-invoices-view)) offer no change to that invoice.

### 15.31 Company Profile

Criteria for the singleton company-profile row ([data-model.md §5.17](data-model.md#517-company-profile-entity), [api.md §14.2.15](api.md#14215-company-profile-operations)).

- **AC-300** `[crit]`: The `company_profile` table carries exactly one row, enforced by a CHECK on a constant primary key (parity with [data-model.md §5.9](data-model.md#59-backup-status-entity)). The row is pre-seeded by the baseline migration with empty mandatory fields. A direct INSERT of a second row is rejected by the CHECK constraint. A direct DELETE of the row is rejected. The application API exposes no path to create or delete — only `GET` + `PUT` (upsert) per [api.md §14.2.15](api.md#14215-company-profile-operations).
- **AC-301** `[crit]`: `GET /api/company-profile` succeeds for every authenticated role (owner, office, worker, bookkeeper) returning the singleton row. `PUT /api/company-profile` succeeds for owner only; office, worker, bookkeeper all receive `403 NOT_PERMITTED`. Unauthenticated requests on either endpoint return `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
- **AC-302** `[crit]`: A successful `PUT /api/company-profile` produces exactly one `audit_log` row via the single-write-path helper ([AC-177](#1523-audit-log)) with `actorKind = 'user'`, `entityType = 'company_profile'`, `action = 'update'`, `entityId` matching the singleton row's id, ancestor pair null (top-level entity, parity with `customer` / `user`). `payload.before` reflects the row state read inside the mutation's transaction before the write; `payload.after` carries the values that landed.
- **AC-303** `[crit]`: `PUT /api/company-profile` rejects a body with `companyName`, `address.street` / `address.zip` / `address.city`, `taxId` or `ustId` empty, null or missing with `422 VALIDATION_ERROR`. `details` names every offending field path. No partial mutation persists.
- **AC-304** `[crit]`: At invoice issuance, the snapshot of `Invoice.issuer` is **taken from the `company_profile` row at the moment the issue transaction reads it**. A subsequent `PUT /api/company-profile` modifying any snapshotted field does not change the issued invoice's `issuer` block — verified by issuing an invoice, mutating the profile (e.g. address change), re-fetching the issued invoice, and asserting `Invoice.issuer.address` equals the snapshot-time value, not the post-mutation value. The rendered binary descriptor on the row continues to point at the bytes produced at issuance; no re-render path is exposed by the spec.
- **AC-305** `[crit]`: Issuing an invoice when the singleton `company_profile` row lacks a required field ([data-model.md §5.17](data-model.md#517-company-profile-entity)) is rejected `422 VALIDATION_ERROR` with `code = COMPANY_PROFILE_REQUIRED` and `details.missingFields` enumerating the missing field paths. The check runs in the issuance transaction, after the sequence allocation lock is acquired but before the increment is committed — a rejection releases the lock without persisting the increment (gapless property is preserved). No `audit_log` row is written for the failed issue.

### 15.32 Activity Dock

Criteria for the app-shell live activity dock ([ui/index.md §8.1.2](ui/index.md#812-authenticated-state)), a privileged-only realtime consumer of the audit feed.

- **AC-317** `[vis]`: While the activity dock is expanded, an audit event committed by another session appears in it within 2 seconds with no manual refresh on the observing session, driven by the `audit_changed` event over `/api/events` ([api.md §14.2.13](api.md#14213-realtime-events), [AC-320](#1528-realtime-events)) and a refetch of [api.md §14.2.8](api.md#1428-audit-log). Parity with [AC-277](#1528-realtime-events) for project lifecycle.
- **AC-318** `[vis]`: The dock is collapsible and default-collapsed; its collapse state persists across view navigation within a session (it does not reset on a view switch). It renders only on desktop viewports — hidden on phones, parity with the Footer ([ui/index.md §8.1.2](ui/index.md#812-authenticated-state)); mobile users reach the same history through the Aktivität view ([ui/management.md §8.13](ui/management.md#813-audit-view)). It exposes an `"Ältere anzeigen"` affordance to page older entries. The dock fetches the **full RBAC-scoped feed** ([AC-180](#1523-audit-log)) — recipient-scope narrowing ([AC-200](#1524-notifications)) is a notifications concern and is not applied here. The dock surface is "everything the caller may read", so every committed `audit_log` row the caller has scope for reaches it.
- **AC-319** `[crit]`: The dock is rendered only to callers holding `audit:read` (owner and office under the default matrix); worker and bookkeeper never see it. Its content is fetched through the `audit:read`-gated [api.md §14.2.8](api.md#1428-audit-log), and no audit content reaches a caller lacking `audit:read` through any channel — the SSE stream carries only the contentless `audit_changed` envelope ([AC-320](#1528-realtime-events)) and the read endpoint enforces the permission gate ([AC-180](#1523-audit-log)).
- **AC-339** `[vis]`: Each dock row is a **single line** in the form `Aktor · Projekt · Beschreibung` with the timestamp aligned to the right. The line never wraps — `Beschreibung` truncates with a trailing ellipsis when the row overflows. Timestamps always render as `DD.MM.YYYY HH:mm` (German locale, the same `formatDateTimeDE` used by the Aktivität table) regardless of how old the row is, so cross-day scanning stays unambiguous. The detail drawer (`"Details anzeigen"` / payload diff) is **not** rendered on the dock — the dock is a glanceable strip, and the detailed payload view lives on the Aktivität page ([ui/management.md §8.13.1](ui/management.md#8131-list)). `Projekt` is the parent project's label snapshot ([data-model.md §5.10](data-model.md#510-audit-log-entity) — `ancestorEntityLabel`) for child entities (`project_worker`, `attachment`, `invoice`) and the project's own `entityLabel` for project rows; rows without a project ancestor (`customer`, `user`, `company_profile`, `data_import`) render an em dash in that slot.
- **AC-340** `[crit]`: A global keyboard shortcut **`Alt+A`** toggles the dock's expanded/collapsed state from any view (mnemonic for _Aktivität_). The shortcut is active for callers who hold `audit:read` — for callers without the permission the dock is absent ([AC-319](#1532-activity-dock)) and the handler is not installed. The dock's header button renders the shortcut hint inline as `Aktivität (Alt+A)` so the affordance is discoverable without external documentation. Letter-key shortcuts match on **either** `event.key` (Windows / Linux / German keyboard) **or** `event.code` (e.g. `KeyA`) so macOS Option+letter still fires the binding — Option remaps `event.key` to a dead-key glyph (`Option+A → å`) but `event.code` keeps the physical position, and matching either preserves the mnemonic on every platform. The handler calls `event.preventDefault()` on the matched `keydown` so the keystroke does not also trigger the browser's menu-bar mnemonic (Firefox / Chrome on Windows / Linux) or leak the macOS dead-key glyph into the document. The handler is suppressed while any element with an editable affordance has focus — `<input>` (text-like types), `<textarea>`, `<select>`, `contenteditable`, or any ARIA `role="textbox"` / `role="searchbox"` widget — so the shortcut does not steal keystrokes typed into filter fields, dropdowns, or AI-prompt-style composers.
- **AC-341** `[vis]`: The activity dock is hidden while the Aktivität view ([ui/management.md §8.13](ui/management.md#813-audit-view)) is the active view — the page already renders the full audit table, so a second feed below it is redundant. Hiding is driven by the client-side router's active-view key (the same key that maps 1:1 to `/audit`), so navigation away from `/audit` restores the dock in its prior collapse state. The `Alt+A` shortcut ([AC-340](#1532-activity-dock)) remains installed for `audit:read` callers; the handler is suppressed while the Aktivität view is active so the keystroke is not silently swallowed by a stale handler (same suppression style as the focus-in-input check in [AC-340](#1532-activity-dock)).
- **AC-342** `[vis]`: The Aktivität view ([ui/management.md §8.13.1](ui/management.md#8131-list)) renders a **`project`** column between `actor` and `entity` (column-key vocabulary mirrors the existing English keys in [ui/management.md §8.13.1](ui/management.md#8131-list); the rendered table header is the German label `"Projekt"`). Each row's project cell shows the parent project's label snapshot ([data-model.md §5.10](data-model.md#510-audit-log-entity) — `ancestorEntityLabel`) for child entities (`project_worker`, `attachment`, `invoice`) and the project's own `entityLabel` for `entityType = 'project'` rows. For entity types with no project ancestor (`customer`, `user`, `company_profile`, `data_import`) the cell renders an em dash. The column is read-only — there is no sort affordance and no dedicated filter; users narrow the feed by `entityType = 'project'` plus the existing `entityLabelQuery`.

### 15.33 Threshold Monitor

Criteria for the periodic evaluator that produces the two non-mutation catalog events ([architecture.md §11.15](architecture.md#1115-threshold-monitor)). Both event classes shipped with a catalog entry, a seeded owner rule, and a push template but **no producer** — these criteria pin the producer.

- **AC-355** `[crit]`: On each sweep the monitor derives the backup badge state ([AC-171](#1522-backup-and-recovery)) from `meta_backup_status` and publishes `backup.failed` when that state is anything other than green, carrying the derived `kind` and `reason` in the system payload. A green state publishes nothing. A state derived from row **age** alone (`backup-stale`, `backup-aging`, `drill-expired`, `drill-stale`, and the never-run states) publishes on the same terms as a failed run. A reason names the subsystem that is actually late: a drill past its red line reports `drill-expired`, not `backup-stale`, so the push cannot tell the owner their backup is out of date while it is fresh and succeeding — this is the only surface that covers a `backup` container which never starts, since a process that is not running cannot publish its own failure. When the status row is unreadable (DB unreachable → the `unknown` state) the monitor publishes nothing and logs the skip: the publisher resolves rules and recipients from that same database, so no push is reachable.
- **AC-356** `[crit]`: When `STORAGE_QUOTA_GB` is declared, the monitor publishes `disk.threshold_reached` once global stored **ciphertext** — the stored total ([data-model.md §5.14](data-model.md#514-storage-usage)) — reaches `THRESHOLD_MONITOR.storageWarnPercent` of the declared capacity, carrying used bytes, capacity, and the rounded fill percentage. Hidden bytes count: they occupy the bucket until the lifecycle rule reaps them. Plaintext is not the measure — the cap describes provisioned bucket capacity, which the encrypted object occupies. Below the band nothing is published. With `STORAGE_QUOTA_GB` unset the storage check does not run at all (no roll-up query) and the skip is logged once at startup. The band is **warn-only**: no upload is rejected on account of it.
- **AC-357** `[crit]`: A condition notifies on entry, then at most once per `THRESHOLD_MONITOR.repeatMinutes` while it remains true. A condition whose derived reason changes (e.g. amber `backup-aging` → red `backup-stale`) notifies immediately, without waiting out the window. A condition that clears and later returns notifies again on its return. Storage overage is keyed on the crossing, not the percentage, so further uploads past the line do not each produce a notification, and the band carries hysteresis: a standing warning is forgotten only once usage falls `THRESHOLD_MONITOR.storageClearMarginPoints` below the warn line. Without that margin, usage oscillating around the band — a reap dipping it under, the next upload pushing it back over — would notify on every re-crossing, because each crossing reads as a fresh condition and bypasses the repeat window. The de-duplication state is process-local; a restart may replay at most one notification per standing condition.
- **AC-358** `[crit]`: The `backup.failed` push body carries the badge's own German label for the derived reason ([ui/index.md §8.1.2](ui/index.md#812-authenticated-state)), so the push and the badge the owner lands on cannot disagree about what is wrong; an absent or unrecognised reason falls back to the generic German sentence. The `disk.threshold_reached` body carries the fill percentage (`Speicher zu N% belegt.`), falling back to the generic sentence when no numeric percentage is supplied. The `backup.failed` **event label** is `Backup-Warnung` — deliberately broader than the class id, because the monitor fires the class for any non-green state and not only a failed run; the id keeps its spelling as the stored `notification_rule` discriminator.
- **AC-359** `[crit]`: The two checks are independent within a sweep — a failure in the backup check does not prevent the storage check from running (or the reverse), and the sweep still reports failure to the scheduler afterwards so the shared sustained-failure backoff engages. A programmer error on one side must not silently disable the other side indefinitely.
