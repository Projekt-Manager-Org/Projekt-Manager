# API Specification

## 14. API Specification

The API is the boundary between the front end and all persistent state ([architecture.md §11.1](architecture.md#111-mandatory-constraints)). The front end's state layer is a client of this API (see [architecture.md §11.3](architecture.md#113-state-layer-behavioral-contract)).

### 14.1 Design Principles

- **Single source of truth.** The API is authoritative for all persisted data.
- **Stack-agnostic contract.** Operations, inputs, and outputs — not transport, URLs, or serialization.
- **Consistent error representation.** Machine-readable code + human-readable message (see [§14.4](#144-error-handling)).
- **Stateless requests.** Each request carries all context needed, including authentication.
- **Pagination-ready.** List operations accept `offset`/`limit`. The contract must support pagination even if the current data volume does not require it.
- **Stable list order.** List operations return rows in a deterministic order — a second fetch yields the same sequence, and pagination pages do not overlap or skip rows.
- **Timestamps managed server-side.** `createdAt`, `updatedAt`, `statusChangedAt` are set by the server, never by clients.

**Precedence.** This document is the normative contract. `docs/api/openapi.json` is a machine-readable artifact _generated from the implementation_ (AC-351) covering the request surface only; it is a derived view, not a second contract. Where the two disagree, this document wins and the divergence is a defect in the code or in §14.2 — never a reason to edit the generated file. See [ARCHITECTURE.md § API Surface](../../ARCHITECTURE.md#api-surface).

#### 14.2.6 Data Extraction

All extraction operations require an authenticated session and the `customer:write` permission. See [ADR-0016](../adr/0016-llm-email-extraction-via-server-proxied-openrouter.md) for the server-side proxy rationale.

| Operation         | Input                  | Output                                                                                                                   | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Extract email** | `text`: raw email text | `{ customer: { name, phone, email, street, zip, city }, project: { title, description } }` — all fields nullable strings | Routes the text to an external LLM via a server-side proxy. The text must be non-empty and not exceed 50,000 characters. The operation is read-only with respect to persistence — it returns extracted data for review; the client uses the existing customer and project creation operations ([AC-518](verification.md#1511-customer-management), [AC-475](verification.md#1512-projects)) to persist the reviewed result. Requires `customer:write` permission. |

Design notes:

- **Stateless with respect to persistence.** The extraction endpoint does not create, update, or delete any record. It is a pure read: email text in, structured data out.
- **Upstream failures are mapped to error categories.** Missing upstream configuration, a non-OK response from the external service, an empty response, or an unparseable response all resolve to a server error (see [§14.4.1](#1441-error-categories)). Internal details (service name, upstream status codes, stack traces) are not exposed.
- **Every field may be null.** The LLM returns `null` for information it could not find in the input. Clients must handle nulls across all fields.

#### 14.2.7 Backup Status

The Layer 2 backup-freshness badge ([verification.md §15.22](verification.md#1522-backup-and-recovery), [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md)) is consumed only by the authenticated owner. The status fields piggyback on the two session-establishment responses, `POST /api/auth/login` and `GET /api/auth/me` — no dedicated route. The earlier unauthenticated `GET /api/backup/status` endpoint was removed together with the login-screen badge surface.

Design notes:

- **Owner-only payload.** Both `/api/auth/login` and `/api/auth/me` include the `backupStatus` field for callers with role `owner`; the field is omitted for every other role. Absence drives the client's "no badge on this surface" branch. The two session-establishment paths are kept symmetric on purpose — a log-out/log-in without this parity leaves the badge stuck on the last `/me`-hydrated value until a full reload, which is the class of staleness AC-171 rules out.
- **Unreachable source → field omitted, not silence.** Misleading state is a critical defect class ([ADR-0014](../adr/0014-ac-tier-system-critical-vs-design.md)). When the status row is unreachable, the server omits the field; the client maps `undefined` to the explicit "Status unbekannt" badge state ([AC-171](verification.md#1522-backup-and-recovery)).
- **No errors on absence of prior runs.** The pre-seed row from the baseline migration is always present. The service reports `lastBackupOk=false` with `lastBackupAt=null` for a DB that has never run a backup; the client derives the `backup-never-run` badge reason from that shape.

#### 14.2.8 Audit Log

A read-only surface over [`audit_log`](data-model.md#510-audit-log-entity). The table is append-only ([data-model.md §6.10](data-model.md#610-audit-log-retention)); no create, update, or delete operation is exposed.

| Operation              | Input                                                                                                                                           | Output                                 | Notes                                                                                                                                                                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List audit entries** | optional: offset, limit, filters: `entityType`, `entityId`, `ancestorType`, `ancestorId`, `entityLabelQuery`, `actorId`, `from`, `to`, `action` | audit entry list, total count          | Returns entries visible to the authenticated caller per the scoping rules below. Ordered by `createdAt` descending (newest first), stable tiebreaker `id`. Default page size matches other list endpoints. Requires `audit:read` permission. Filters AND-compose. |
| **Get audit entry**    | audit entry id                                                                                                                                  | single entry, or not-found / forbidden | Returns the full entry subject to the scoping rules below. Requires `audit:read` permission.                                                                                                                                                                      |

Design notes:

- **RBAC-sliced reads.** A single scope predicate — `auditDestructiveScopeForCaller(user)` — composes at the repository layer, following the pattern established in [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md) (permissions stay coarse; scope is orthogonal to capability). For owner the predicate returns null (no filter); for every other role that holds `audit:read` (office under the current matrix) it returns a `WHERE` fragment excluding destructive entries, defined as: `action = 'purge'` on any entity type; `action = 'delete'` AND `entityType = 'user'`; `action = 'update'` AND `entityType = 'user'` where the payload diff touches `roles`. The predicate AND-composes with the permission gate. An earlier revision also carried a reachability predicate for workers (self-authored + project-reachability); it was removed when workers lost `audit:read` — the audit surface is administrative, not worker-facing.
- **Three-way result (same as ADR-0019).** Get-by-id distinguishes three outcomes: not-found (`404 NOT_FOUND`), in-scope (`200`), out-of-scope (`403 NOT_PERMITTED` — only the destructive-action narrowing can produce this, and only for office). Out-of-scope must not be collapsed to not-found — the caller-identity boundary matters for the same reasons as in [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md).
- **Actor name in response.** For a `user`-actor entry, the response includes the acting user's `displayName` as a derived read-time convenience — independent of whether the caller holds `user:read`. The field is a presentation aid for the activity feed; it is not a substitute for the `user` list endpoint and carries no additional user-record fields. System-actor entries include `actorReason` instead.
- **Entity filters.** `entityId` takes a UUID and matches rows equal to that id. `ancestorType` + `ancestorId` take the same shape and match rows whose write-time ancestor pair equals `(ancestorType, ancestorId)` ([architecture.md §11.12](architecture.md#1112-audit-ancestor-link)) — this is the filter the project-detail activity feed uses so the one call returns project rows plus every nested-entity row (`project_worker`, `attachment`) scoped to that project. `entityLabelQuery` takes a case-insensitive substring of at least three characters and matches rows whose frozen `entityLabel` contains it — it powers the Aktivität filter bar, where the caller types a name. LIKE metacharacters are escaped (`%`, `_`, `\`) so user input is treated literally. Rows whose `entityLabel` is null (import and retention paths that cannot supply a label) are excluded from `entityLabelQuery` matches by construction. The substring match is backed by a pg_trgm GIN index on `entity_label`; sub-three-character queries are rejected (422) to keep the index useful. Ancestor filters are served by the compound index `audit_log_ancestor_idx`.
- **Ancestor label in response.** Each entry includes `ancestorEntityLabel` — the parent project's label snapshot captured at write time ([data-model.md §5.10](data-model.md#510-audit-log-entity)). Null for entries without a project ancestor (`customer`, `user`, `company_profile`, `data_import`). Powers the Aktivität view's `Projekt` column ([verification.md AC-342](verification.md#1532-activity-dock)) and the activity dock's single-line row ([verification.md AC-339](verification.md#1532-activity-dock)) without a runtime JOIN against `projects`.
- **Payload drawer.** Entries include `payload` as returned. The client renders the diff drawer only on rows with a non-null, non-empty payload.
- **Pagination and ordering.** Entries are ordered newest-first by `createdAt`, with `id` as the deterministic tiebreaker. A second fetch with the same filters yields the same sequence; pages do not overlap or skip rows (per [§14.1](#141-design-principles)).
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED` (authentication error).
  - Authenticated caller lacks `audit:read` → `403 NOT_PERMITTED` (authorization error).
  - Get-by-id on an existing row outside the caller's scope → `403 NOT_PERMITTED` (authorization error — see three-way result above).
  - Get-by-id on a non-existent row → `404 NOT_FOUND`.
  - Filter or pagination parameters failing schema validation → `422 VALIDATION_ERROR`.
  - `from`/`to` inverted (`to < from`) → `422 VALIDATION_ERROR`.
  - `entityType`, `ancestorType`, or `action` filter values outside the documented enum / vocabulary ([data-model.md §5.10](data-model.md#510-audit-log-entity)) → `422 VALIDATION_ERROR`.
- **Post-commit publisher contract.** The notification publisher module exposes:
  - `onAuditCommitted(handler)` — registers a handler invoked with the committed audit entry after the domain transaction commits. Handlers are invoked once per commit, in registration order.
  - `setOperationalLogger(logger)` — wires the structured operational logger used to surface handler failures.
    A throwing handler does not roll back the originating mutation — see [AC-183](verification.md#1523-audit-log) for the failure-surface contract. The publisher is process-local; restart-durability is out of scope (in-process dispatch per [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)).

#### 14.2.9 Notification Rules

Admin-editable rules mapping the closed event catalog ([data-model.md §5.11](data-model.md#511-notification-rule)) to recipient specs. CRUD is gated on `notifications:manage` and follows the validation rules below ([ADR-0023](../adr/0023-notification-rules-db-stored-closed-event-catalog.md)).

| Operation       | Input                                                        | Output                 | Notes                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List rules**  | optional: offset, limit                                      | rule list, total count | All rules. Ordered by `eventClass` ascending, `createdAt` ascending as tiebreaker. Requires `notifications:manage`.                                                                    |
| **Get rule**    | rule id                                                      | single rule            | Full rule or not-found. Requires `notifications:manage`.                                                                                                                               |
| **Create rule** | eventClass, stateFilter?, recipientSpec, enabled             | created rule           | `recipientSpec` must carry at least one non-empty part. `stateFilter` permitted only on `project.transition_forward` / `project.transition_backward`. Requires `notifications:manage`. |
| **Update rule** | rule id, eventClass?, stateFilter?, recipientSpec?, enabled? | updated rule           | PATCH — omitted fields unchanged. Same validation as create. `eventClass` is updatable. Requires `notifications:manage`.                                                               |
| **Delete rule** | rule id                                                      | success/failure        | Hard-deletes. No soft-delete — rules are configuration. Requires `notifications:manage`.                                                                                               |

Design notes:

- **Validation rules** (all raise validation error on breach):
  - `eventClass` must be a member of [`NotificationEventClass`](data-model.md#511-notification-rule).
  - `stateFilter` must be null unless `eventClass` is a transition event; when present, it must be a member of the configured workflow-state set ([index.md §3](index.md#3-workflow-states)).
  - `recipientSpec.roles` must be a subset of the configured role set ([index.md §4.2](index.md#42-roles)); `userIds` must each reference an active `UserAccount`; `includeAssignedWorkers` is rejected when `eventClass` is a non-project-scoped event (`backup.failed`, `disk.threshold_reached`).
  - At least one of `roles`, `includeAssignedWorkers`, or `userIds` must resolve to a non-empty part — an enabled rule with an empty spec is rejected.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Caller lacks `notifications:manage` → `403 NOT_PERMITTED`.
  - Get / update / delete on an unknown id → `404 NOT_FOUND`.
  - Validation breaches above → `422 VALIDATION_ERROR`.
- **Take-effect semantics.** A successful create, update, or delete affects the next event committed after the change; in-flight events use the rule set read at their own commit.
- **No uniqueness constraint on `(eventClass, stateFilter, recipientSpec)`.** Duplicates are permitted; the publisher's recipient-union dedups by `user_id` at resolution. A uniqueness constraint would force admins to reason about rule-equivalence — exactly the complexity the flat model avoids ([ADR-0023](../adr/0023-notification-rules-db-stored-closed-event-catalog.md)).

#### 14.2.10 Push Subscription

Browser push subscription management. Authenticated self-scope — a caller manages only their own subscriptions. The VAPID public-key read is the only unauthenticated route in this section (the key is intentionally public; the private half never leaves the server).

| Operation                 | Input                                     | Output                             | Notes                                                                                                                                 |
| ------------------------- | ----------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Read VAPID public key** | —                                         | `{ vapidPublicKey: string\|null }` | Unauthenticated. Returns the server-derived VAPID public key, or `null` when VAPID credentials are not configured on the server.      |
| **Subscribe to push**     | endpoint, keys (p256dh, auth), userAgent? | success/failure                    | Registers a subscription for the authenticated caller. Re-subscribing an existing `endpoint` updates the row rather than duplicating. |
| **Unsubscribe from push** | endpoint (or subscription id)             | success/failure                    | Removes one of the caller's subscriptions. Unknown endpoints / ids are idempotent no-ops.                                             |

Design notes:

- **VAPID key is server-sourced.** The client fetches the public key at subscribe time from the read endpoint; the server derives it from the private half at startup, so the operator maintains a single server-side secret. Short HTTP cache (5 minutes) — a deploy rotates the key and the browser cache expires well inside one user session.
- **Ownership is derived.** The server sets `userId` from the session; a client-supplied user id is refused ([§14.4.2](#1442-error-principles)).
- **Self-scoped lookups.** Subscribe / unsubscribe filter by `(subscription.id OR endpoint, userId = session.userId)` before acting. An id or endpoint belonging to another user is treated as unknown — the no-op response is indistinguishable from a truly-unknown one. Rationale: self-scope endpoints must not enumerate other users' subscriptions.
- **No auto-request.** The permission prompt is user-initiated from the settings affordance ([ui/index.md §8.7.2](ui/index.md#872-user-menu)); the server never pushes a registration on login.
- **Dispatch-time pruning.** A subscription the browser reports permanently dead at dispatch is removed server-side — housekeeping, not a user-facing operation.
- **Mute interaction.** `pushMuted = true` suppresses delivery to every subscription the user owns; rows are retained, so unmuting restores delivery without a re-subscribe.
- **Rate limiting.** Mutation paths (`POST`, `DELETE`) share a per-session mutation bucket ([architecture.md §12.2 rate-limit config](architecture.md#122-company-configurable-settings) `[C]`); exceeding returns `429 RATE_LIMITED`. The VAPID public-key read is not rate-limited (unauthenticated, GET-only, 5-minute cache).
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED` (subscribe / unsubscribe only; the VAPID read is unauthenticated).
  - Malformed `endpoint` / `keys` → `422 VALIDATION_ERROR`.
  - `endpoint` exceeds 2048 characters, `keys.p256dh` or `keys.auth` exceeds 512 characters, or `endpoint` is not a syntactically valid URI → `422 VALIDATION_ERROR` (bounded to protect the subscription table from pathological input).

#### 14.2.13 Realtime Events

Single multiplexed Server-Sent Events channel (`GET /api/events`) that pushes invalidation hints to authenticated clients so cross-session UI surfaces refetch the read endpoints they already consume. Architectural rationale and shape are pinned by [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md); the bus and emission topology are described in [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel). v1 consumers:

- The storage-usage UI — the `storage_usage_changed` event invalidates the Footer badge ([ui/index.md §8.1.2](ui/index.md#812-authenticated-state)) and the DatenView storage row ([ui/daten.md §8.11.3](ui/daten.md#8113-speichernutzung)), which then show the new totals ([AC-450](verification.md#1529-storage-usage)).
- The project list / detail surfaces — the `project_changed` event invalidates the project list ([ui/management.md §8.8](ui/management.md#88-project-management-view)), the Kanban and Calendar views ([ui/workflow-views.md §8.2](ui/workflow-views.md#82-kanban-view), [§8.3](ui/workflow-views.md#83-calendar-view)), and the project detail panel / page ([ui/workflow-views.md §8.4](ui/workflow-views.md#84-project-detail-panel), [ui/project-detail.md §8.15](ui/project-detail.md#815-project-detail-page)), which then refetch the project.
- The attachment surfaces — the `attachment_changed` event invalidates the project's photo gallery / binary list and Papierkorb ([ui/project-detail.md §8.15](ui/project-detail.md#815-project-detail-page)), which then refetch the per-project attachment list(s).
- The invoice surfaces — the `invoice_changed` event invalidates the invoice list and per-project invoice block ([ui/invoices.md §8.16](ui/invoices.md#816-invoices-view), [ui/project-detail.md §8.15.11](ui/project-detail.md#81511-invoice)), which then refetch [§14.2.14](#14214-invoice-operations).
- The activity surfaces — the `audit_changed` event invalidates the project-detail activity feed ([ui/workflow-views.md §8.4.1](ui/workflow-views.md#841-activity-feed)), the global Aktivität view ([ui/management.md §8.13](ui/management.md#813-audit-view)), and the activity dock ([ui/index.md §8.1.2](ui/index.md#812-authenticated-state)), which then refetch [§14.2.8](#1428-audit-log).
- The data-exchange UI — the `data_exchange_job_changed` event invalidates the Daten-view export / import dialogs ([ui/daten.md §8.11.1](ui/daten.md#8111-export), [§8.11.2](ui/daten.md#8112-import)), which then refetch the active job.

| Operation     | Input | Output                                                                                                               | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------------- | ----- | -------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Subscribe** | —     | `text/event-stream` — a long-lived response carrying typed `event:` frames and 25-second `:` heartbeat comment lines | Authenticated via the existing session middleware ([§14.3](#143-authorization-rules)); rejected with `401 UNAUTHENTICATED` / `SESSION_EXPIRED` for unauthenticated callers. Connection persists until the client disconnects (tab close, navigation away, network drop), the server restarts, or the session is revoked / expires / the user is deactivated mid-stream — see "Mid-stream session re-validation" below. The client uses the browser-native `EventSource`; cookies ride along automatically. No `Cache-Control` directive — `text/event-stream` is non-cacheable per the WHATWG SSE protocol. No audit row (the channel is a read; no domain mutation). |

Design notes:

- **One channel, typed events.** All event kinds ride a single response stream and are discriminated by the `event:` field. v1 catalog:
  - `storage_usage_changed` — emitted post-commit from every byte-moving mutation site ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Consumers: Footer badge, DatenView row ([AC-450](verification.md#1529-storage-usage)).
  - `project_changed` — emitted post-commit from every project-row mutation site and every customer edit ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Consumers refetch the project list and detail.
  - `attachment_changed` — emitted post-commit from every attachment mutation that changes a project's attachment list ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Co-emitted with `storage_usage_changed`. Consumers refetch the per-project attachment list(s). Pinned by [AC-336](verification.md#1528-realtime-events).
  - `invoice_changed` — emitted post-commit from every invoice-row mutation site ([architecture.md §11.14](architecture.md#1114-invoice-domain)): draft CRUD, issue, cancel; a customer edit that changes a draft's recipient ([data-model.md §5.15](data-model.md#515-invoice-entity)); project archive and restore, which change the invoices' `projectArchived` ([§14.2.14](#14214-invoice-operations)); and project purge, direct or through customer delete, whose cascade removes the project's drafts. Consumers refetch the invoice list / detail read endpoints in [§14.2.14](#14214-invoice-operations).
  - `audit_changed` — emitted post-commit once per committed `audit_log` row, via the notification publisher's `onAuditCommitted` hook ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)). Consumers refetch the audit read endpoint in [§14.2.8](#1428-audit-log).
  - `data_exchange_job_changed` — emitted post-write on every full-account export / import job lifecycle transition and a throttled subset of progress updates ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [data-model.md §5.18](data-model.md#518-data-exchange-job)). Consumers refetch the active job ([AC-602](verification.md#1514-data-exchange)).

  The catalog is open-extensible per [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md) — new event names land here as the consuming surfaces are specified, without new infra.

- **Payload shape.** Each event is an invalidation hint, not a data payload. The `data:` line carries a small typed JSON envelope (e.g. `{ "type": "storage_usage_changed" }`, `{ "type": "project_changed" }`, or `{ "type": "invoice_changed" }`) that mirrors the event name; it is forward-compatible with carrying a non-sensitive correlation field if a consumer ever needs one. Sensitive content is never on the wire — the client refetches via the gated read endpoint that already serves it (`storage_usage_changed` ⇒ refetch the storage totals; `project_changed` ⇒ refetch the project reads; `invoice_changed` ⇒ refetch [§14.2.14](#14214-invoice-operations)). Single source of truth, no two-channel sync.
- **Authorization model.** Authentication at the channel; authorization at the consumer endpoint. Events broadcast to every connected authenticated session — event names carry no information beyond "a thing of kind X changed", and the role-leakage tradeoff is acknowledged and accepted under the project's threat model in [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md). Sensitive content remains behind the consumer endpoints' role gates (e.g. `data:export` for the storage totals, [§14.3](#143-authorization-rules)).
- **Heartbeat.** A 25-second comment line (`:` keepalive) defeats reverse-proxy and browser idle disconnects. The interval is configurable **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)) — default 25 seconds, bounded 1 s … 600 s.
- **Mid-stream session re-validation.** The authentication preHandler runs once at connect time, so the server bounds a held stream's lifetime to the session that authorized it. Each heartbeat tick re-validates the session ([CWE-613](https://cwe.mitre.org/data/definitions/613.html)); a deleted row (logout / reaper / `UserService.deactivateUser` cascade), an `expiresAt` in the past, or `users.active = false` ends the response stream within one heartbeat interval. Architectural detail in [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel); verification in [§15.28](verification.md#1528-realtime-events) AC-275.
- **Reconnect semantics.** Browser-native auto-reconnect via `EventSource` at the implementation-defined reconnection time mandated by the WHATWG SSE spec (overridable by the server's `retry:` field, not used here). No `Last-Event-ID` replay — events are invalidation hints, not a log; on reconnect the client refetches state via the existing read endpoints. Server restart drops every connection; clients reconnect and refetch (acceptable, parity with [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)'s in-process publisher).
- **Reverse proxy posture.** Caddy auto-flushes responses with `Content-Type: text/event-stream`; the deployment configuration carries an explicit `flush_interval -1` directive on the `/api/events` upstream as defensive belt-and-suspenders ([architecture.md §11.6](architecture.md#116-deployment-topology), [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)).
- **No caching contract.** No `Cache-Control` headers. The protocol is incompatible with caching by design.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`. The connection is rejected; no stream begins.
- **Verification.** The channel shape, auth, broadcast reach, heartbeat, and per-emitter delivery are pinned by [§15.28](verification.md#1528-realtime-events) — `storage_usage_changed` emission by AC-270, `project_changed` emission by [AC-276](verification.md#1528-realtime-events), `attachment_changed` emission by [AC-336](verification.md#1528-realtime-events). The subscribe-side coverage guard (every catalog event has ≥1 client subscriber) is pinned by [AC-338](verification.md#1528-realtime-events). Consumer-side refresh behavior and the multi-user value tests live in [§15.29](verification.md#1529-storage-usage) (storage usage), [AC-277](verification.md#1528-realtime-events) (project lifecycle), and [AC-337](verification.md#1528-realtime-events) (attachments).

Design notes:

- **Number allocation is part of issuance, not creation.** A draft has no `number`; issuance is the only path that allocates. The row-exclusive lock on `invoice_sequence` (taken by the atomic `INSERT … ON CONFLICT … DO UPDATE … RETURNING` — [data-model.md §6.13](data-model.md#613-gapless-sequence-allocation)) is held until the issuance transaction commits, so a failure at any later step (render, binary write, audit) returns the value to the sequence — gaplessness is by construction.
- **Snapshot moment is the issue call, not the draft.** `Invoice.issuer` is copied from the live `company_profile` at the issue call: a draft created today and issued next month carries next month's company profile (per [data-model.md §5.17](data-model.md#517-company-profile-entity)). `Invoice.recipient` is frozen as the draft holds it, overrides included; customer corrections reach the draft when they are saved ([data-model.md §5.15](data-model.md#515-invoice-entity)).
- **Pre-issuance validation.** The issue call rejects when (a) the `company_profile` row lacks a required field ([data-model.md §5.17](data-model.md#517-company-profile-entity); `COMPANY_PROFILE_REQUIRED`), (b) `performanceDate` is null (`VALIDATION_ERROR`), (c) `lines` is empty (`VALIDATION_ERROR`), (d) the parent project is not in `rechnung_faellig` (`INVOICE_PROJECT_STATE`), (e) the draft has already been concurrently mutated to a non-draft state (`CONFLICT`), or (f) a stored line or a derived total breaks a §5.15 rule ([AC-384](verification.md#1530-invoices); `VALIDATION_ERROR`).
- **Line totals are server-derived.** Create draft and Update draft take lines without `lineTotal`; the server derives it from `quantity` and `unitPrice` ([data-model.md §5.15](data-model.md#515-invoice-entity)). A client-sent `lineTotal` is refused ([§14.4.2](#1442-error-principles)); a `unitPrice` with more than 4 decimals is rejected.
- **Edit optimistic concurrency.** Update draft, Delete draft and Issue invoice require `expectedVersion`; check order per [data-model.md §6.4](data-model.md#64-concurrency). A rejected issue writes nothing and allocates no number.
- **Calendar-valid dates.** Every `YYYY-MM-DD` field on the wire (`performanceDate`, `issueDate`, …) must round-trip exactly through a calendar-arithmetic check on create / update. A structurally valid but calendar-invalid date (e.g. `2026-02-30`, `2025-04-31`) is rejected `422 VALIDATION_ERROR` rather than silently normalized by `Date` parsing. Silent normalization would land in the immutable issued snapshot, `factur-x.xml`, and the rendered PDF — a §147 AO / GoBD defect.
- **Cancellation creates a sibling, not a soft-delete.** Issued invoices are write-once at the persistence layer ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)); the only mutation allowed is the cancellation flip on the original row's `status`, paired with the Storno row's creation. Cancelling an already-cancelled row returns `INVOICE_ALREADY_CANCELLED` (`409`).
- **PDF download contract.** The PDF/A-3 bytes ride the same e2e-encryption pipeline as attachments ([ADR-0024](../adr/0024-binary-attachment-e2e-encryption.md)) — encrypted at issuance, stored as ciphertext. This gated route is their only read path: the attachment surface never addresses a rendered invoice PDF ([AC-364](verification.md#1530-invoices)). The route returns either the decrypted bytes or a presigned-GET URL paired with the unwrapped DEK material; the transport is implementation-defined.
- **Project archive state.** Every invoice in a response carries `projectArchived`, true while its project is archived, so a client withholds the changes the server refuses ([AC-513](verification.md#1530-invoices), [AC-514](verification.md#1530-invoices)).
- **Audit ancestor.** Every invoice mutation writes an `audit_log` row through `mutate()` ([architecture.md §11.3](architecture.md#113-state-layer-behavioral-contract)); the row's `entityType = 'invoice'`, `entityId = <invoice id>`, ancestor `('project', projectId)` ([architecture.md §11.12](architecture.md#1112-audit-ancestor-link)). The project-detail activity feed surfaces invoice events alongside attachments and project transitions in one indexed predicate.
- **SSE.** Invoice mutations emit `invoice_changed` post-commit; emitters: [§14.2.13](#14213-realtime-events). The client refetches the gated list / detail endpoint. The event name is registered with the SSE event-name registry alongside `storage_usage_changed` and `project_changed`.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Caller lacks the relevant invoice permission → `403 NOT_PERMITTED`.
  - Update / delete on a non-draft row → `422 VALIDATION_ERROR` with `code = INVOICE_FROZEN`.
  - Update / delete / issue with a stale `expectedVersion` → `409 CONFLICT` with `code = VERSION_CONFLICT`; a missing one → `422 VALIDATION_ERROR`.
  - Issue on a draft whose project is not in `rechnung_faellig` → `409 CONFLICT` with `code = INVOICE_PROJECT_STATE`.
  - Create / update with a `taxMode` outside §5.15 `TaxMode` → `422 VALIDATION_ERROR`.
  - Create / update / issue whose lines or derived totals break a §5.15 rule ([AC-384](verification.md#1530-invoices)) → `422 VALIDATION_ERROR`.
  - Issue with an incomplete company profile → `422 VALIDATION_ERROR` with `code = COMPANY_PROFILE_REQUIRED` and `details.missingFields` enumerating the missing field names.
  - Issue / cancel on a missing id → `404 NOT_FOUND`.
  - Create / update / delete / issue / cancel on an archived project → `404 NOT_FOUND` ([AC-285](verification.md#1530-invoices), [AC-513](verification.md#1530-invoices)).
  - Cancel on an already-cancelled invoice → `409 CONFLICT` with `code = INVOICE_ALREADY_CANCELLED`.
  - Cancel on a draft → `409 CONFLICT` with `code = INVOICE_NOT_ISSUED`.
  - Download PDF on a draft → `409 CONFLICT` with `code = INVOICE_NOT_ISSUED`.
  - Bulk export supplying both selectors, or neither → `422 VALIDATION_ERROR`.
  - Bulk export whose id selection includes a draft → `422 VALIDATION_ERROR` with `code = DRAFT_NOT_EXPORTABLE` and `details.invoiceId` naming the draft.
  - Bulk export whose filter matches more rows than the server's ceiling → `422 VALIDATION_ERROR` with `code = EXPORT_TOO_LARGE` and `details.total` / `details.cap`.

- **Bulk export decides its status before it streams.** Every selected invoice is resolved and its bytes obtained before the first byte of the archive is written. Once the archive begins streaming the status code is already committed, so a fault discovered mid-build can only reach the client as a truncated download — which is indistinguishable from a dropped connection. The ceiling on the selection exists to keep that pre-resolution bounded.

| -------------------------- | ----------------------------------------------------------------------------------------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Get company profile**    | —                                                                                                     | company profile | Returns the singleton row. | **Upsert company profile** | expectedVersion, companyName, address, taxId, ustId, iban?, accentColor?, footerText?, defaultTaxMode | updated profile | Owner-only upsert. Design notes:

- **Singleton, no POST / DELETE.** The row is pre-seeded by the baseline migration with empty mandatory fields ([data-model.md §5.17](data-model.md#517-company-profile-entity)); the API exposes a read and an upsert only. Trying to create a second row or delete the row is not addressable.
- **Owner-only writes.** Reads are gated by an authenticated session (every authenticated role may read — the profile is referenced by invoice rendering and by the data view); writes require the owner role. The single permission is folded into the owner-only role check (no separate `company_profile:read` / `company_profile:write` keys are introduced — adding one for every owner-only singleton dilutes the permission catalog). The route layer enforces the role check; the service layer rejects non-owner writes defensively.
- **Required fields** ([data-model.md §5.17](data-model.md#517-company-profile-entity)). The upsert rejects an empty one; issuance re-checks them ([`COMPANY_PROFILE_REQUIRED`](#144-error-handling)), because the stored row can be incomplete.
- **Audit posture.** Each upsert produces one `audit_log` row via the single-write-path helper. Ancestor pair is null (top-level entity, parity with `customer` / `user`).
- **SSE.** Company-profile changes do not emit `invoice_changed` — issued invoices snapshot their issuer at issuance time and are unaffected by subsequent profile edits. The Daten view's company-profile form refetches on its own form-save success.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Non-owner caller on PUT → `403 NOT_PERMITTED`.
  - Stale `expectedVersion` → `409 CONFLICT` with `code = VERSION_CONFLICT`; nothing is written.
  - Body with an empty required field, or any field violating its schema (length, type, format) → `422 VALIDATION_ERROR` with `details` naming the offending field path.

### 14.4 Error Handling

Every error response carries two components:

| Component                  | Purpose                               | Example                                                   |
| -------------------------- | ------------------------------------- | --------------------------------------------------------- |
| **Machine-readable code**  | Programmatic handling by the client   | `INVALID_CREDENTIALS`, `SESSION_EXPIRED`, `NOT_PERMITTED` |
| **Human-readable message** | Display to the user (German, **[C]**) | `"Anmeldung fehlgeschlagen"`, `"Sitzung abgelaufen"`      |

An optional third component, `details`, may carry structured validation information (e.g., field-level errors from schema validation). Clients should handle its absence gracefully.

#### 14.4.1 Error Categories

The API must distinguish the following error categories. Each category has distinct client-side handling (see [ui/behavior.md — Asynchronous Mutation Behavior](ui/behavior.md#95-asynchronous-mutation-behavior)).

| Category                 | Meaning                                                                                                                                                                                                                                                         | Client behavior                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authentication error** | Credentials invalid, session expired, or session absent.                                                                                                                                                                                                        | Redirect to login screen. Show expiry message if session was previously valid.                                                                                 |
| **Authorization error**  | User is authenticated but lacks permission for the requested operation (e.g., changing another user's password).                                                                                                                                                | Show error message. Do not redirect to login.                                                                                                                  |
| **Validation error**     | Request is malformed or violates business rules (e.g., transition from `erledigt`, missing required field, invalid dates).                                                                                                                                      | Show error message. Revert optimistic update if applicable.                                                                                                    |
| **Not found**            | The requested entity (project or user ID) does not exist.                                                                                                                                                                                                       | Show error message. Re-fetch project list to sync state.                                                                                                       |
| **Route not found**      | No handler is registered for the request's method and URL — an unknown URL, or a known one under a verb it does not serve. Distinct from "Not found" above — the latter signals a known endpoint with an absent entity; this signals a stale client or a probe. | Show generic error message. Do not redirect.                                                                                                                   |
| **Gone**                 | The entity existed but is permanently unavailable; retry will not help (e.g., a Papierkorb row whose source bytes were lifecycle-reaped ahead of the row reaper, see [AC-424](verification.md#1526-attachments)).                                               | Show error message. Do not retry.                                                                                                                              |
| **Conflict**             | The mutation cannot proceed because the resource state has changed since it was read (e.g., concurrent state transition) or the operation conflicts with related state (e.g., deleting a customer with active projects).                                        | Refetch resource state. Optionally retry against the new state.                                                                                                |
| **Idempotency conflict** | A create request carried a client-supplied `id` that already identifies a row, but one or more user-supplied fields in the request body differ from the stored row ([AC-127](verification.md#1517-data-integrity)).                                             | Close the create form, refresh the affected list, surface the message. Do not retry the same id with the same body — the request is ambiguous by construction. |
| **Server error**         | Unexpected internal failure.                                                                                                                                                                                                                                    | Show generic error message. Do not expose internal details.                                                                                                    |
| **Rate limited**         | Too many requests in the configured time window.                                                                                                                                                                                                                | Show retry message. Back off before retrying.                                                                                                                  |

The full set of machine-readable error codes: `INVALID_CREDENTIALS`, `UNAUTHENTICATED`, `SESSION_EXPIRED`, `NOT_PERMITTED`, `VALIDATION_ERROR`, `CONFLICT`, `IDEMPOTENCY_CONFLICT`, `VERSION_CONFLICT`, `NOT_FOUND`, `ROUTE_NOT_FOUND`, `GONE`, `RATE_LIMITED`, `SCHEMA_VERSION_MISMATCH`, `TARGET_NOT_EMPTY`, `RESTORE_CONFIRMATION_MISMATCH`, `MISSING_USER_REFS`, `EXPORT_JOB_ACTIVE`, `IMPORT_JOB_ACTIVE`, `EXPORT_JOB_NOT_READY`, `UPLOAD_OFFSET_CONFLICT`, `UPLOAD_TOO_LARGE`, `UPLOAD_NOT_ACCEPTED`, `BULK_LIMIT_EXCEEDED`, `DEK_UNWRAP_FAILED`, `INVOICE_FROZEN`, `INVOICE_PROJECT_STATE`, `INVOICE_NOT_ISSUED`, `INVOICE_ALREADY_CANCELLED`, `DRAFT_NOT_EXPORTABLE`, `EXPORT_TOO_LARGE`, `COMPANY_PROFILE_REQUIRED`, `CUSTOMER_HAS_INVOICES`, `PROJECT_HAS_INVOICES`, `USER_HAS_INVOICES`, `IMPORT_DROPS_ISSUED_INVOICES`, `SERVER_ERROR`.

<!-- CHECKED:error-codes:END -->

`EXPORT_JOB_ACTIVE` / `IMPORT_JOB_ACTIVE` (409) signal a create request colliding with an export / import job already `pending` or `running` ([AC-331](verification.md#1514-data-exchange)); the response carries the active job's id so the client re-attaches rather than starting a second. `EXPORT_JOB_NOT_READY` (409) is a download requested before the build finished. `UPLOAD_OFFSET_CONFLICT` (409) is a resumable-upload chunk PATCHed at an offset other than the server's current one. `UPLOAD_NOT_ACCEPTED` (409) is a chunk PATCHed to an import job that is no longer `pending` — the upload already completed (the job is `running` or terminal), or the id is not an import job at all; the normal client loop ends at `Upload-Length` before the flip, so this guards direct API misuse (e.g. PATCHing an export job's id to fire a bogus restore). All five are conflict-category codes — the client resolves them by re-reading job / upload state, not by re-authenticating. `UPLOAD_TOO_LARGE` (413) is a resumable-upload chunk whose bytes would extend past the declared `Upload-Length`; the server offset does not advance and the client retries with at most the remaining length.

`TARGET_NOT_EMPTY` (409) is a conflict-category code; `RESTORE_CONFIRMATION_MISMATCH`, `SCHEMA_VERSION_MISMATCH` and `MISSING_USER_REFS` (422) are validation-category codes ([§15.14](verification.md#1514-data-exchange)).

`VERSION_CONFLICT` (409) is a versioned edit whose `expectedVersion` no longer matches the stored row ([data-model.md §6.4](data-model.md#64-concurrency)); nothing was written. A conflict-category code, distinct from `CONFLICT` so the client runs stale-write recovery ([ui/behavior.md §9.5](ui/behavior.md#95-asynchronous-mutation-behavior)) rather than a generic refetch.

`DEK_UNWRAP_FAILED` is also a specialization of the validation-error category (`422`) — a per-row attachment envelope cannot be unwrapped against the loaded binary keyring (corrupt envelope, or a key not in the keyring). The Service Worker translates the code to the [AC-244](verification.md#1526-attachments) "Schlüssel nicht verfügbar" placeholder render path.

The invoice-domain codes are specializations of the validation-error and conflict categories:

- **`INVOICE_FROZEN`** (`422`) — mutation rejected because the invoice is `issued` or `cancelled` ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)). Client should refetch and present a read-only viewer.
- **`INVOICE_PROJECT_STATE`** (`409`) — issue rejected because the parent project is not in `rechnung_faellig`. Client refetches the project status and surfaces the mismatch (the project may have moved while the draft was open).
- **`INVOICE_NOT_ISSUED`** (`409`) — cancel / download-PDF rejected on a draft. Client surfaces the message; the affordance should not have been presented (a client-state-drift indicator).
- **`INVOICE_ALREADY_CANCELLED`** (`409`) — cancel on a row whose `status` is already `'cancelled'`. Idempotent intent is acceptable, but the route does not silently succeed — the operator's view of the invoice should be refreshed before a re-cancel attempt.
- **`COMPANY_PROFILE_REQUIRED`** (`422`) — issue rejected because the singleton `company_profile` row lacks a required field ([data-model.md §5.17](data-model.md#517-company-profile-entity)). `details.missingFields` enumerates the missing field paths (e.g. `["companyName", "address.zip", "ustId"]`). Client routes the owner to the Daten view's company-profile form ([ui/daten.md §8.11.4](ui/daten.md#8114-company-profile)).
- **`CUSTOMER_HAS_INVOICES`** (`409`) — [AC-532](verification.md#1511-customer-management). There is no remediation path — issued / cancelled rows are subject to §147 AO retention.
- **`DRAFT_NOT_EXPORTABLE`** (`422`) — bulk export rejected because at least one requested invoice id resolves to a draft. Drafts carry no rendered PDF, so including one would either bundle an empty document or fail mid-stream after bytes have already left the wire. `details.invoiceId` is the offending draft so the client can target the row in the user's selection. Raised in ids-mode only; in filter-mode drafts are silently outside the filter. See [§14.2.14](#14214-invoice-operations).
- **`EXPORT_TOO_LARGE`** (`422`) — bulk export rejected because the filter matches more invoices than the server will bundle into one archive. `details.total` is the matched-row count and `details.cap` the ceiling, so the client can phrase a precise message. The caller narrows the filter (typically by year) and retries. See [§14.2.14](#14214-invoice-operations).
- **`PROJECT_HAS_INVOICES`** (`409`) — project hard-delete (`DELETE /api/projects/:id/purge`) rejected because the project carries any **issued or cancelled** `Invoice` row ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices), [§6.6](data-model.md#66-referential-integrity)). Draft invoices on the project cascade-delete with the purge and do not trigger this code. `details.invoiceCount` carries the count of issued + cancelled rows. Distinct from `CONFLICT` (used for purging a non-archived project, AC-503) so the client can render the targeted invoice-notice copy rather than the generic archive-first hint.
- **`USER_HAS_INVOICES`** (`409`) — user hard-delete rejected because an **issued or cancelled** `Invoice` row references the user as `createdBy` or `updatedBy` ([data-model.md §6.9](data-model.md#69-soft-deletes)). References on drafts do not trigger this code. `details.invoiceCount` carries the count of those rows. The German message points to deactivation as the remedy.
- **`IMPORT_DROPS_ISSUED_INVOICES`** (`409`) — [AC-367](verification.md#1514-data-exchange). The remedy is an archive exported after the latest issuance. The import job ends `failed` with the code's message as `error_detail`.

#### 14.4.2 Error Principles

- **Authentication errors are distinguishable from authorization errors.** An expired session must not produce the same error as an insufficient permission — the client handles them differently (redirect vs. inline message).
- **Undefined input is refused.** A request body carrying a field the operation does not define, at any depth, is rejected as a validation error and changes nothing. Rationale: a client sending a stale or misspelled field must learn its request was not understood ([AC-516](verification.md#1517-data-integrity)).
- **Validation errors are structured.** When a mutation is rejected for business rule violations, the error must identify which rule was violated (e.g., "cannot transition from terminal state") so the client can render a meaningful message.
- **Error messages never leak internal details.** No stack traces, database field names, table names, file paths, or query information in any error response. This applies to all error categories including server errors.
- **HTTP statusCode reflects the failure class.** A request rejected at the transport layer (malformed body declared as JSON, payload exceeding configured limits, unsupported media type, request whose method and URL match no registered handler) preserves the 4xx HTTP statusCode native to that failure and surfaces a stable machine-readable code. Transport-layer rejections are never collapsed into a 5xx response, and they are not logged at the operational `error` level (used to back 5xx alerting on logs). Rationale: 5xx must mean "the server failed", not "the client made a recoverable mistake"; conflating the two — either through the wire response or through the log severity — trains operators to ignore real 5xx incidents.
