# API Specification

---

## 14. API Specification

The API is the boundary between the front end and all persistent state ([architecture.md §11.1](architecture.md#111-mandatory-constraints)). The front end's state layer is a client of this API (see [architecture.md §11.3](architecture.md#113-state-layer-behavioral-contract)).

### 14.1 Design Principles

- **Single source of truth.** The API is authoritative for all persisted data.
- **Stack-agnostic contract.** Operations, inputs, and outputs — not transport, URLs, or serialization.
- **Consistent error representation.** Machine-readable code + human-readable message (see [§14.4](#144-error-handling)).
- **Stateless requests.** Each request carries all context needed, including authentication.
- **Pagination-ready.** List operations accept `offset`/`limit`. The contract must support pagination even if the current data volume does not require it.
- **Stable list order.** List operations return rows in a deterministic order — a second fetch yields the same sequence, and pagination pages do not overlap or skip rows.
- **Timestamps managed server-side.** `createdAt`, `updatedAt`, `statusChangedAt` are set by the server, never by clients.

**Precedence.** This document is the normative contract. `docs/api/openapi.json` is a machine-readable artifact _generated from the implementation_ (AC-351) covering the request surface only; it is a derived view, not a second contract. Where the two disagree, this document wins and the divergence is a defect in the code or in §14.2 — never a reason to edit the generated file. See [ARCHITECTURE.md § API Surface](../../ARCHITECTURE.md#api-surface).

Design notes:

- Failed login returns a generic error — no distinction between "user not found" and "wrong password".
- User profiles never include `passwordHash`.
- **Update self** is restricted to the caller's own record. The endpoint cannot affect any other user and does not accept a user ID. Identity-bearing fields (`username`, `roles`, `active`) are never updatable through this operation — those remain administrative (see [§14.2.3](#1423-user-management)).
- **Update self error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)): missing or invalid session → authentication error; request body violating the allowed value set (e.g., `themePreference` outside `'light' | 'dark' | 'system'`, `pushMuted` not a boolean) → validation error.

Design notes:

- Plaintext passwords are never stored or logged. The server hashes before storage.
- **Username is immutable** after creation.
- Users can be deactivated or hard-deleted. Deactivation preserves the record; deletion removes it. See [data-model.md §6.9](data-model.md#69-soft-deletes).
- **Self-deactivation and self-deletion are prohibited.**
- Password-change session side effects: see [data-model.md §5.4](data-model.md#54-session).

#### 14.2.4 Unified Data Exchange

Full-account data exchange has **two surfaces**, both built on the business-data envelope ([data-model.md §5.8](data-model.md#58-export-envelope)):

- The **business-data services** — `ExportService` and `ImportService` — exchange the envelope only (business rows; no attachment bytes). They are **internal**: there is no standalone HTTP route — the seed and the export/import jobs call them directly. They anchor the CI roundtrip ([AC-141](verification.md#1514-data-exchange)) and are the building block the jobs use for the business-data leg. Per-entity bulk surfaces do not exist.
- The **export / import jobs** — `POST /api/export-jobs` and `POST /api/import-jobs` — are the operator-facing full-account takeout: the envelope **plus every `status='ready'` attachment's plaintext bytes**, bundled into one archive the server builds (export) or restores (import). The job runs server-side and asynchronously; the browser triggers it, polls status over the job's REST surface, and downloads (export) or uploads (import) the archive. Plaintext archives stage only on the VPS, inside the trust radius; B2 holds only per-attachment ciphertext bytes ([ADR-0024 §Full-account takeout](../adr/0024-binary-attachment-e2e-encryption.md)).

Only the jobs are surfaced as Daten-view actions ([ui/daten.md §8.11](ui/daten.md#811-daten-view)); the business-data services are an internal + CI surface. The three-layer persistence model lives in [ADR-0018](../adr/0018-data-persistence-and-recovery-layered-strategy.md); the job lifecycle entity in [data-model.md §5.18](data-model.md#518-data-exchange-job-entity).

The `attachments` slot is not consumed here — attachment bytes are restored by the import **job** server-side (Import-job notes below); the business-data import restores business-data rows only. When override wipes `users`, the caller's session is CASCADE-dropped — `sessionInvalidated: true` (see "Session invalidation on user wipe" below). |

Design notes:

- **Envelope shape** — `{ schema_version: int, exported_at: ISO 8601 string, users: EnvelopeUser[], company_profile: EnvelopeCompanyProfile[], customers: EnvelopeCustomer[], projects: EnvelopeProject[], project_workers: { projectId, userId }[], invoices: EnvelopeInvoice[], invoice_sequence: EnvelopeInvoiceSequence[], attachments: EnvelopeAttachment[] }`. Each entity carries every persisted field including `id`, audit timestamps, archive state, frozen snapshot blocks, and (for users) `passwordHash`; canonical wire types and per-field semantics live in [data-model.md §5.8](data-model.md#58-export-envelope). `company_profile` is a singleton-array (always length `1`). `invoices` is ordered `(cancellation_of NULLS FIRST, id)` so the slot satisfies the `cancellationOf` self-FK on insert (see "Invoice ordering" below).
- **Override flag** — selected via the `override` option. When the target is non-empty, override wipes the expanded business-data set (`users`, `company_profile`, `customers`, `projects`, `project_workers`, `invoice_sequence`, `invoices`) AND the `attachments` table atomically with the restore. Without the flag, a non-empty target rejects the request with a specific error code. The wipe-and-restore runs as a single transaction: an insert-time failure rolls back both the wipe and any rows already inserted. An override that would drop an issued or cancelled invoice — the envelope lacks its id and number pair — is rejected with `IMPORT_DROPS_ISSUED_INVOICES` before the wipe ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)). `invoice_sequence` is never lowered: per `(year, kind)` the higher of target and envelope value survives ([data-model.md §6.13](data-model.md#613-gapless-sequence-allocation)).
- **Confirmation phrase** — when `override` is set AND the target is non-empty, the call MUST supply `confirmationPhrase` equal to the configured phrase **[C]**. The comparison trims leading/trailing whitespace and is case-sensitive. A missing or non-matching phrase is rejected with a specific error code and performs no writes. Override-into-empty-target requests are exempt. The phrase is a destructive-action guard, not an authorization factor; the authoritative gate remains `data:restore`.
- **Missing user references** — the user-id fields carried in the envelope (`customers.createdBy`, `customers.updatedBy`, `projects.createdBy`, `projects.updatedBy`, `project_workers.userId`, `invoices.createdBy`, `invoices.updatedBy`, `company_profile.updatedBy`) are checked against the envelope's own `users[]` slot during envelope validation. With `users` in the envelope, the happy path produces no missing references — the slot is self-contained. The check stays as defense-in-depth: a hand-edited envelope, a partial export reconstructed by hand, or a malformed third-party-produced envelope can still reference a user id absent from `envelope.users`. Null or missing values on the nullable audit fields (`createdBy`, `updatedBy` — see [data-model.md §5.1](data-model.md#51-project-entity), [§5.6](data-model.md#56-customer-entity), and the policy in [AC-98](verification.md#1517-data-integrity)) are not treated as references and do not trigger the check. A value is counted as a missing reference only when it is present in the envelope and absent from `envelope.users[]`. If any referenced user id is absent, the import is rejected with error code `MISSING_USER_REFS` and performs no writes. Rationale: with users now in the envelope, the divergence the code surfaces is internal to the envelope itself — the right remediation is to **re-export from a complete source**, not to restore Layer 2. The error is not papered over by silently nulling the references.
- **Validation ordering** — on the commit path, intra-envelope referential integrity is reported first under `VALIDATION_ERROR`; the missing-user-reference check runs only when the envelope is intra-consistent, and `MISSING_USER_REFS` is raised only on an intra-consistent envelope — never both codes in one response. Rationale: both failures point at the same remediation class (re-export from a complete source), but `MISSING_USER_REFS` carries the targeted `details.references` payload identifying every offending site, and surfacing it alongside other intra-envelope errors would muddy that signal.
- **Invoice tax mode, lines and totals** — envelope validation checks every invoice's `taxMode`, `lines` and `totals` against the write rules of [data-model.md §5.15](data-model.md#515-invoice-entity), in every `status`; `totals` must equal the ones derived from `lines` and `taxMode`. A violation is a `422 VALIDATION_ERROR` issue; a conforming row is inserted unchanged, never re-derived ([AC-386](verification.md#1514-data-exchange)).
- **Atomic failure** — if any row fails validation during an import (with or without override), no state change is persisted. The request has no partial outcome. The missing-user-reference check participates in this guarantee: detection happens in envelope validation, before any wipe or insert runs.
- **Schema version** — a monotonic integer. Exports stamp the current value; imports compare and reject mismatches outright (see [ADR-0018 §Decision](../adr/0018-data-persistence-and-recovery-layered-strategy.md#decision)).
- **Import is text-only.** The business-data import ignores any `attachments` key on the envelope and never inserts attachment rows ([AC-253](verification.md#1514-data-exchange)); it restores `schema_version`, `exported_at`, `users`, `company_profile`, `customers`, `projects`, `project_workers`, `invoices`, `invoice_sequence` only. The `attachments` slot rides only on the **export** envelope as a metadata-only descriptor ([data-model.md §5.8](data-model.md#58-export-envelope)); attachment **bytes** are restored exclusively by the import **job** (Import-job notes below), which re-encrypts each file server-side under the importing instance's `BINARY_AGE_RECIPIENT` and PUTs ciphertext to B2 — no key material rides the envelope. Rationale: never landing an attachment row whose wrapped DEK was minted on the exporting instance avoids a silent-data-loss class — it would be unwrappable on the importing one, so every download of that attachment would 404.
- **Override wipes the expanded business-data set.** When `override=true` AND the target is non-empty, the wipe phase clears `users`, `company_profile`, `customers`, `projects`, `project_workers`, `invoice_sequence`, `invoices`, AND `attachments` atomically with the restore. The phase does not touch object storage; orphaned B2 keys are reaped by the existing orphan reaper ([AC-408](verification.md#1526-attachments)). Wipe and restore run inside a single transaction — a row failure during insert rolls back both. Insert order satisfies the envelope's FK direction (`users → company_profile → customers → projects → project_workers → invoice_sequence → invoices`); within `invoices`, originals (`cancellationOf IS NULL`) are inserted before Stornos so the self-FK is satisfied without a deferrable constraint.
- **Session invalidation on user wipe.** Override always wipes `users` and TRUNCATEs `sessions` in the same transaction, so the caller's running session is dropped — `sessions.userId` is `ON DELETE CASCADE` per [§5.4](../spec/data-model.md#54-session), so the `users` delete would drop it regardless. The response on the override-into-non-empty-target path carries `sessionInvalidated: true`; on the empty-target path (no `users` row to CASCADE) it carries `sessionInvalidated: false`. Response shape: `{ schema_version, summary, sessionInvalidated: boolean }`. The flag is the wire-contract signal; the mechanism is the FK cascade — no separate session-reaper call. The full-account import **job** wraps this: it re-authenticates the operator after the wipe and re-attaches to the running job, with no bearer token in play (Import-job — session invalidation below). Pinned by [AC-310](verification.md#1514-data-exchange).
- **Single import audit row.** The import writes **exactly one** `audit_log` row per import, regardless of how many entity slots the envelope populated. The row carries `actorKind = 'system'`, `actorReason = 'data_import'`, `action = 'import_restored'`, `entityType = 'data_import'` (a synthetic `AuditEntityType` declared in [data-model.md §5.10](data-model.md#510-audit-log-entity); no physical table backs it — the value tags a deployment-level event), `entityId` set to a freshly minted UUID (the import batch identifier — not a foreign key to any row), `entityLabel = "Import: <N> Datensätze"` where N is the total row count across all non-empty restored slots, and `payload = { counts: { users, company_profile, customers, projects, project_workers, invoices, invoice_sequence, attachments } }` with every slot key present (zero where empty). The `attachments` count is always 0 for the business-data import ([AC-253](verification.md#1514-data-exchange)) — it never restores attachment rows; the import **job** writes its own single `data_import` row whose `attachments` count is the restored attachment total (Jobs — audit, below). Per-row audit on bulk restore would be 100× the noise without 100× the signal; per-slot audit rows misattributed activity-feed entries to specific entity instances (e.g. "user X.displayName — import_restored" on the first-imported user). One row + the per-slot count map in the payload preserves the forensic trail and the operator-facing summary. Rows on the original instance (issued by ordinary CRUD) survive in the source's audit_log and ride no part of this envelope ([data-model.md §5.8](data-model.md#58-export-envelope) "stays out"). Pinned by [AC-311](verification.md#1514-data-exchange).
- **Invoice ordering and self-FK.** `invoices.cancellationOf` is a nullable self-FK ([§5.15](../spec/data-model.md#515-invoice-entity), [§6.6](../spec/data-model.md#66-referential-integrity)) — non-null only on Storno rows, pointing at the original `invoices.id` they cancel. The envelope orders the slot `(cancellation_of NULLS FIRST, id)` so the importer can satisfy the self-FK on insert without a deferrable constraint: originals land before Stornos that reference them. A Storno whose `cancellationOf` targets an `invoices.id` absent from `envelope.invoices[]` is rejected at envelope validation with `422 VALIDATION_ERROR`; the whole wipe-and-restore transaction is never started. A Storno whose `cancellationOf` targets another Storno (Storno-of-Storno chain) is rejected with the same `422 VALIDATION_ERROR` — real issuance never produces chains (a Storno is terminal), and the two-pass insert partitions on `cancellationOf IS NULL` without topologically ordering Stornos, so a chain would FK-violate at pass 2 even if the originals existed. Pinned by [AC-309](verification.md#1514-data-exchange). The `invoice_sequence` slot is restored in the same transaction (between `project_workers` and `invoices`) so the next-number allocation continues from the imported peak rather than restarting at 1 — pinned by [AC-312](verification.md#1514-data-exchange).
- **Export job — build and lifecycle.** On `POST /api/export-jobs` the job moves `pending → running`: the server materializes the envelope (the `Export` operation above, written to `data.json`), then for each `status='ready'` attachment unwraps the per-row DEK against the loaded binary `age` identity, fetches the ciphertext from B2, AES-256-GCM-decrypts, and streams the plaintext into the archive. The **envelope is the single source of truth** for what the archive contains: the build iterates `data.json`'s `attachments[]` and looks up only the columns the envelope withholds (`original_key`, `wrapped_dek`) by those ids — it never re-derives the set with a second `status='ready'` query, which would see a different snapshot and produce an archive the importer rejects. A per-row unwrap / fetch / decrypt failure **fails the build** — the job moves `failed` with `error_detail` naming the attachment id and no archive is served. On success the job moves `ready` with `archive_ref` set to the VPS-staged archive; a wholesale failure (binary identity absent, disk exhausted) also moves it `failed`. There is no partial archive: a `ready` export is a complete, consistent point-in-time snapshot or it does not exist, and a transient fault is answered by re-running the export. Pinned by [AC-322](verification.md#1514-data-exchange) (lifecycle) and [AC-325](verification.md#1514-data-exchange) (completeness).
- **Export job — archive layout + manifest.** The archive is a zip carrying `data.json` (the envelope) and `manifest.json` at the root, plus every `status='ready'` attachment as plaintext bytes under `attachments/<projektnummer>-<projekt-titel>/<attachment-id>-<dateiname>` (each path component sanitised per the file-name rules in [data-model.md §5.13](data-model.md#513-attachment); the prepended `attachment-id` defuses `(projektnummer, dateiname)` collisions). `manifest.json` is `{ manifestVersion: 1, exportedAt, totalFiles, totalBytes, files: [{ zipPath, sizeBytes, sha256, attachmentId? }] }`, computed server-side during the build — the offline-verification surface an external verifier uses to re-derive every entry's SHA-256 (`jq -r '.files[] | "\(.sha256)  \(.zipPath)"'`). The manifest covers exactly the envelope's `attachments[]` — by construction, since the archive set is derived from the envelope ([AC-325](verification.md#1514-data-exchange)). Pinned by [AC-323](verification.md#1514-data-exchange).
- **Export job — download (Range).** `GET /api/export-jobs/:id/download` streams the staged archive only when the job is `ready` (`409 EXPORT_JOB_NOT_READY` otherwise). It is **Range-capable**, so a dropped browser download resumes via an HTTP `Range` request rather than rebuilding the archive. A full response carries `Accept-Ranges: bytes`; a satisfiable `Range` request returns `206 Partial Content` with `Content-Range` + `Content-Length`; an unsatisfiable range returns `416 Range Not Satisfiable` with `Content-Range: bytes */<size>`. Once the staging reaper has swept the artifact the download returns `404`. Pinned by [AC-324](verification.md#1514-data-exchange).
- **Import job — resumable upload.** The archive is uploaded over an offset-based protocol (a tus-style resumable-upload shape): the client declares total size via `Upload-Length` at create, PATCHes chunks each tagged with `Upload-Offset`, and resumes from the server's current offset (read via `HEAD`) after any interruption. The server appends each chunk to the staged file and rejects an offset mismatch with `409 UPLOAD_OFFSET_CONFLICT`, making a retried chunk safe; bytes past `Upload-Length` are rejected with `413 UPLOAD_TOO_LARGE`. This is what lets a multi-GB restore survive a network drop without restarting from zero — the load-bearing reliability property for a full-account archive. Pinned by [AC-326](verification.md#1514-data-exchange).
- **Import job — validate before wipe.** When the upload reaches `Upload-Length` the job moves `pending → running` and the server streams the archive (no whole-archive in-memory unzip), validating `data.json` (`schema_version` equals the current value — else `failed`, `error_detail` carrying `SCHEMA_VERSION_MISMATCH`; intra-envelope referential integrity; `manifest.json` coverage parity + per-entry SHA-256) **before** any destructive write. Any validation failure terminates the job `failed` with `error_detail` and performs no writes — a corrupt, tampered, or wrong-version archive never wipes the target. Pinned by [AC-327](verification.md#1514-data-exchange).
- **Import job — restore.** Business data is restored through the same single transaction the `Import` operation above runs (override wipe of the importable set + `attachments`, IDs preserved, insert order per "Override wipes the expanded business-data set"). Then, per envelope `attachments[]` row, the server reads the matching plaintext entry from the staged archive, generates a fresh DEK, AES-256-GCM-encrypts, wraps the DEK under the instance's `BINARY_AGE_RECIPIENT`, and PUTs ciphertext to B2 — the `attachment` row is created with the envelope's `id` / `createdBy` / `createdAt` preserved, and the PUT's version-id captured into `version_id` (so the restored row hides/restores through the Papierkorb like an uploaded one). For a `kind = 'photo'` row the server also regenerates the gallery thumbnail from the restored original (the takeout bundles only originals — the envelope carries no thumb), encrypts it under its own fresh DEK, PUTs the ciphertext to the `.thumb` key, and sets `hasThumbnail` / `thumbKey` / `wrappedThumbDek` / `ciphertextThumbSizeBytes` / `thumbVersionId`; thumbnail derivation is opportunistic — an undecodable image restores without a thumb rather than failing the job. Because the override wipe clears `attachments` first, each run rebuilds the attachment set from the archive: re-running the job is a deterministic full replace (same `id`s, no duplicate rows) rather than an incremental resume. An attachment that an envelope invoice references via `renderedPdfBinaryDescriptorId` is restored as a rendered invoice PDF — invoice namespace and invoice lock ([data-model.md §5.15](data-model.md#515-invoice-entity)) — so it stays off the attachment surface. The browser is never in the byte path; B2 holds only ciphertext bytes. Pinned by [AC-328](verification.md#1514-data-exchange) and [AC-365](verification.md#1514-data-exchange).
- **Import job — override + confirmation up front.** A non-empty target requires `override: true` AND a matching `confirmation_phrase` **[C]** at `POST /api/import-jobs` — the server checks target-emptiness at create and fails fast — `TARGET_NOT_EMPTY` (missing `override`) or `RESTORE_CONFIRMATION_MISMATCH` (wrong / missing phrase) — **before** the upload, never after a multi-GB transfer. Empty-target imports require neither. The phrase is a destructive-action guard, not an authorization factor; the gate remains `data:restore`. Pinned by [AC-329](verification.md#1514-data-exchange).
- **Import job — session invalidation + re-auth.** The restore wipes `users`, CASCADE-dropping the operator's session mid-job. The job row survives — its `created_by` FK is `ON DELETE SET NULL` ([data-model.md §5.18](data-model.md#518-data-exchange-job-entity)) — and processing continues server-side. The browser's next status poll returns `401`; the operator re-authenticates (their account round-trips through the archive with its original `passwordHash`), re-attaches via `GET /api/import-jobs` (latest), and resumes polling to completion. No bearer token is minted — the job does all byte work server-side under its own loaded identity, so the browser needs no stand-in credential. Pinned by [AC-330](verification.md#1514-data-exchange).
- **Jobs — one active per kind.** At most one export job and one import job may be `pending`/`running` at a time (single-operator, in-process execution — [data-model.md §5.18](data-model.md#518-data-exchange-job-entity)). A create colliding with an active job of the same kind returns `409 EXPORT_JOB_ACTIVE` / `409 IMPORT_JOB_ACTIVE` carrying the active job's id, so the UI re-attaches rather than starting a second. Pinned by [AC-331](verification.md#1514-data-exchange).
- **Jobs — stale staging swept on create.** A `pending`/`running` job blocks a same-kind create (above), but a prior _terminal_ job's staged archive lingers on the VPS-local path until the TTL reaper ([data-model.md §6.15](data-model.md#615-takeout-staging-reaper)). To stop back-to-back jobs accumulating plaintext archives on a finite disk (and exhausting it), each successful create first sweeps every prior terminal job of that kind whose `archive_ref` is still set — deletes the staged file and nulls `archive_ref` (the swept job's download then `404`s, identical to a TTL sweep). When ≥1 artifact was swept, the `201` carries `X-Discarded-Prior-Staged: <n>` (the count; header omitted when nothing was swept) so the UI can tell the operator the previous staged archive was discarded. Bounds staging to the active job plus at most the latest terminal job per kind.
- **Jobs — progress + realtime.** Each lifecycle transition and a throttled subset of progress updates (≈1/s or per-N files, so a thousand-file job is not a thousand frames) emit a `data_exchange_job_changed` SSE frame ([§14.2.13](#14213-realtime-events)). The frame is invalidation-only ([ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md)); the client refetches the job over its REST surface. Lifecycle transitions always emit; progress emission is the only throttled class. Pinned by [AC-333](verification.md#1514-data-exchange).
- **Jobs — audit.** A job writes exactly **one** `audit_log` row at its terminal transition (`ready` or `failed`): `entityType = 'data_import'` (the synthetic deployment-level type, [data-model.md §5.10](data-model.md#510-audit-log-entity)), written at the endpoint / runner layer where actor + request context live. Progress is not audited — it is not a business-entity mutation and does not route through `mutate()`. Pinned by [AC-332](verification.md#1514-data-exchange).
- **Jobs — staging + reaper.** Plaintext archives — export output and import uploads alike — stage on a VPS-local path (`archive_ref`), never on B2 ([ADR-0024](../adr/0024-binary-attachment-e2e-encryption.md) invariant). A scheduled reaper sweeps staged archives — a `ready` export's downloadable artifact and any abandoned or terminal import upload — older than the takeout staging TTL **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)). After a reap an export download returns `404`. Pinned by [AC-334](verification.md#1514-data-exchange).
- **Jobs — error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)): missing / expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`; caller lacking `data:export` (export jobs) or `data:restore` (import jobs) → `403 NOT_PERMITTED`; create colliding with an active job → `409 EXPORT_JOB_ACTIVE` / `409 IMPORT_JOB_ACTIVE`; missing / malformed `Upload-Length` (create) or `Upload-Offset` (chunk) → `400 VALIDATION_ERROR`; download before `ready` → `409 EXPORT_JOB_NOT_READY`; unsatisfiable download `Range` → `416`; upload chunk at a stale offset → `409 UPLOAD_OFFSET_CONFLICT`; upload chunk to a job that is no longer `pending` or to a non-import id → `409 UPLOAD_NOT_ACCEPTED`; bytes past `Upload-Length` → `413`; unknown job id → `404 NOT_FOUND`. Processing failures (schema mismatch, manifest / integrity failure, archive corruption, binary identity absent, disk exhaustion) surface on the job row as `status = 'failed'` + `error_detail`, not as a synchronous HTTP error — the create and upload calls have already returned `2xx` by the time processing runs.

#### 14.2.7 Backup Status

The Layer 2 backup-freshness badge ([verification.md §15.22](verification.md#1522-backup-and-recovery), [ADR-0020](../adr/0020-layer-2-encrypted-r2-backups-with-operator-loaded-drills.md)) is consumed only by the authenticated owner. The status fields piggyback on the two session-establishment responses, `POST /api/auth/login` and `GET /api/auth/me` (see [§14.2.1](#1421-authentication)) — no dedicated route. The earlier unauthenticated `GET /api/backup/status` endpoint was removed together with the login-screen badge surface.

Design notes:

- **Owner-only payload.** Both `/api/auth/login` and `/api/auth/me` include the `backupStatus` field for callers with role `owner`; the field is omitted for every other role. Absence drives the client's "no badge on this surface" branch. The two session-establishment paths are kept symmetric on purpose — a log-out/log-in without this parity leaves the badge stuck on the last `/me`-hydrated value until a full reload, which is the class of staleness AC-171 rules out.
- **Unreachable source → field omitted, not silence.** Misleading state is a critical defect class ([ADR-0014](../adr/0014-ac-tier-system-critical-vs-design.md)). When the status row is unreachable, the server omits the field; the client maps `undefined` to the explicit "Status unbekannt" badge state ([AC-171](verification.md#1522-backup-and-recovery)).
- **No errors on absence of prior runs.** The pre-seed row from the baseline migration is always present. The service reports `lastBackupOk=false` with `lastBackupAt=null` for a DB that has never run a backup; the client derives the `backup-never-run` badge reason from that shape.

#### 14.2.8 Audit Log

A read-only surface over [`audit_log`](data-model.md#510-audit-log-entity). The table is append-only ([data-model.md §6.10](data-model.md#610-audit-log-retention)); no create, update, or delete operation is exposed.

| Operation              | Input                                                                                                                                           | Output                                 | Notes                                                                                                                                                                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List audit entries** | optional: offset, limit, filters: `entityType`, `entityId`, `ancestorType`, `ancestorId`, `entityLabelQuery`, `actorId`, `from`, `to`, `action` | audit entry list, total count          | Returns entries visible to the authenticated caller per the scoping rules below. Ordered by `createdAt` descending (newest first), stable tiebreaker `id`. Default page size matches other list endpoints. Requires `audit:read` permission. Filters AND-compose. |
| **Get audit entry**    | audit entry id                                                                                                                                  | single entry, or not-found / forbidden | Returns the full entry subject to the scoping rules below. Requires `audit:read` permission.                                                                                                                                                                      |

Design notes:

- **RBAC-sliced reads.** A single scope predicate — `auditDestructiveScopeForCaller(user)` — composes at the repository layer, following the pattern established in [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md) (permissions stay coarse; scope is orthogonal to capability). For owner the predicate returns null (no filter); for every other role that holds `audit:read` (office under the current matrix) it returns a `WHERE` fragment excluding destructive entries, defined as: `action = 'purge'` on any entity type; `action = 'delete'` AND `entityType = 'user'`; `action = 'update'` AND `entityType = 'user'` where the payload diff touches `roles`. The predicate AND-composes with the permission gate. An earlier revision also carried a reachability predicate for workers (self-authored + project-reachability); it was removed when workers lost `audit:read` — the audit surface is administrative, not worker-facing.
- **Three-way result (same as ADR-0019).** Get-by-id distinguishes three outcomes: not-found (`404 NOT_FOUND`), in-scope (`200`), out-of-scope (`403 NOT_PERMITTED` — only the destructive-action narrowing can produce this, and only for office). Out-of-scope must not be collapsed to not-found — the caller-identity boundary matters for the same reasons as in [AC-147](verification.md#1521-role-scoping).
- **Actor name in response.** For a `user`-actor entry, the response includes the acting user's `displayName` as a derived read-time convenience — independent of whether the caller holds `user:read`. The field is a presentation aid for the activity feed; it is not a substitute for the `user` list endpoint and carries no additional user-record fields. System-actor entries include `actorReason` instead.
- **Entity filters.** `entityId` takes a UUID and matches rows equal to that id. `ancestorType` + `ancestorId` take the same shape and match rows whose write-time ancestor pair equals `(ancestorType, ancestorId)` ([architecture.md §11.12](architecture.md#1112-audit-ancestor-link)) — this is the filter the project-detail activity feed uses so the one call returns project rows plus every nested-entity row (`project_worker`, `attachment`) scoped to that project. `entityLabelQuery` takes a case-insensitive substring of at least three characters and matches rows whose frozen `entityLabel` contains it — it powers the Aktivität filter bar, where the caller types a name. LIKE metacharacters are escaped (`%`, `_`, `\`) so user input is treated literally. Rows whose `entityLabel` is null (import and retention paths that cannot supply a label) are excluded from `entityLabelQuery` matches by construction. The substring match is backed by a pg_trgm GIN index on `entity_label`; sub-three-character queries are rejected (422) to keep the index useful. Ancestor filters are served by the compound index `audit_log_ancestor_idx`.
- **Ancestor label in response.** Each entry includes `ancestorEntityLabel` — the parent project's label snapshot captured at write time ([data-model.md §5.10](data-model.md#510-audit-log-entity)). Null for entries without a project ancestor (`customer`, `user`, `company_profile`, `data_import`). Powers the Aktivität view's `Projekt` column ([verification.md AC-342](verification.md#1532-activity-dock)) and the activity dock's single-line row ([verification.md AC-339](verification.md#1532-activity-dock)) without a runtime JOIN against `projects`.
- **Payload drawer.** Entries include `payload` as returned. The client renders the diff drawer only on rows with a non-null, non-empty payload.
- **Pagination and ordering.** Entries are ordered newest-first by `createdAt`, with `id` as the deterministic tiebreaker. A second fetch with the same filters yields the same sequence; pages do not overlap or skip rows (per [§14.1](#141-design-principles)).
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED` (authentication error).
  - Authenticated caller lacks `audit:read` → `403 NOT_PERMITTED` (authorization error).
  - Get-by-id on an existing row outside the caller's scope → `403 NOT_PERMITTED` (authorization error — see three-way result above).
  - Get-by-id on a non-existent row → `404 NOT_FOUND`.
  - Filter or pagination parameters failing schema validation → `422 VALIDATION_ERROR`.
  - `from`/`to` inverted (`to < from`) → `422 VALIDATION_ERROR`.
  - `entityType`, `ancestorType`, or `action` filter values outside the documented enum / vocabulary ([data-model.md §5.10](data-model.md#510-audit-log-entity)) → `422 VALIDATION_ERROR`.
- **Post-commit publisher contract.** The notification publisher module exposes:
  - `onAuditCommitted(handler)` — registers a handler invoked with the committed audit entry after the domain transaction commits. Handlers are invoked once per commit, in registration order.
  - `setOperationalLogger(logger)` — wires the structured operational logger used to surface handler failures.
    A throwing handler does not roll back the originating mutation — see [AC-183](verification.md#1523-audit-log) for the failure-surface contract. The publisher is process-local; restart-durability is out of scope (in-process dispatch per [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)).

#### 14.2.9 Notification Rules

Admin-editable rules mapping the closed event catalog ([data-model.md §5.11](data-model.md#511-notification-rule)) to recipient specs. CRUD is gated on `notifications:manage` and follows the validation rules below ([ADR-0023](../adr/0023-notification-rules-db-stored-closed-event-catalog.md)).

| Operation       | Input                                                        | Output                 | Notes                                                                                                                                                                                  |
| --------------- | ------------------------------------------------------------ | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **List rules**  | optional: offset, limit                                      | rule list, total count | All rules. Ordered by `eventClass` ascending, `createdAt` ascending as tiebreaker. Requires `notifications:manage`.                                                                    |
| **Get rule**    | rule id                                                      | single rule            | Full rule or not-found. Requires `notifications:manage`.                                                                                                                               |
| **Create rule** | eventClass, stateFilter?, recipientSpec, enabled             | created rule           | `recipientSpec` must carry at least one non-empty part. `stateFilter` permitted only on `project.transition_forward` / `project.transition_backward`. Requires `notifications:manage`. |
| **Update rule** | rule id, eventClass?, stateFilter?, recipientSpec?, enabled? | updated rule           | PATCH — omitted fields unchanged. Same validation as create. `eventClass` is updatable. Requires `notifications:manage`.                                                               |
| **Delete rule** | rule id                                                      | success/failure        | Hard-deletes. No soft-delete — rules are configuration. Requires `notifications:manage`.                                                                                               |

Design notes:

- **Validation rules** (all raise validation error on breach):
  - `eventClass` must be a member of [`NotificationEventClass`](data-model.md#511-notification-rule).
  - `stateFilter` must be null unless `eventClass` is a transition event; when present, it must be a member of the configured workflow-state set ([index.md §3](index.md#3-workflow-states)).
  - `recipientSpec.roles` must be a subset of the configured role set ([index.md §4.2](index.md#42-users)); `userIds` must each reference an active `UserAccount`; `includeAssignedWorkers` is rejected when `eventClass` is a non-project-scoped event (`backup.failed`, `disk.threshold_reached`).
  - At least one of `roles`, `includeAssignedWorkers`, or `userIds` must resolve to a non-empty part — an enabled rule with an empty spec is rejected.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Caller lacks `notifications:manage` → `403 NOT_PERMITTED`.
  - Get / update / delete on an unknown id → `404 NOT_FOUND`.
  - Validation breaches above → `422 VALIDATION_ERROR`.
- **Take-effect semantics.** A successful create, update, or delete affects the next event committed after the change; in-flight events use the rule set read at their own commit.
- **No uniqueness constraint on `(eventClass, stateFilter, recipientSpec)`.** Duplicates are permitted; the publisher's recipient-union dedups by `user_id` at resolution. A uniqueness constraint would force admins to reason about rule-equivalence — exactly the complexity the flat model avoids ([ADR-0023](../adr/0023-notification-rules-db-stored-closed-event-catalog.md)).

#### 14.2.10 Push Subscription

Browser push subscription management. Authenticated self-scope — a caller manages only their own subscriptions. The VAPID public-key read is the only unauthenticated route in this section (the key is intentionally public; the private half never leaves the server).

| Operation                 | Input                                     | Output                             | Notes                                                                                                                                 |
| ------------------------- | ----------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Read VAPID public key** | —                                         | `{ vapidPublicKey: string\|null }` | Unauthenticated. Returns the server-derived VAPID public key, or `null` when VAPID credentials are not configured on the server.      |
| **Subscribe to push**     | endpoint, keys (p256dh, auth), userAgent? | success/failure                    | Registers a subscription for the authenticated caller. Re-subscribing an existing `endpoint` updates the row rather than duplicating. |
| **Unsubscribe from push** | endpoint (or subscription id)             | success/failure                    | Removes one of the caller's subscriptions. Unknown endpoints / ids are idempotent no-ops.                                             |

Design notes:

- **VAPID key is server-sourced.** The client fetches the public key at subscribe time from the read endpoint; the server derives it from the private half at startup, so the operator maintains a single server-side secret. Short HTTP cache (5 minutes) — a deploy rotates the key and the browser cache expires well inside one user session.
- **Ownership is derived.** The server sets `userId` from the session; a client-supplied user id is ignored.
- **Self-scoped lookups.** Subscribe / unsubscribe filter by `(subscription.id OR endpoint, userId = session.userId)` before acting. An id or endpoint belonging to another user is treated as unknown — the no-op response is indistinguishable from a truly-unknown one. Rationale: self-scope endpoints must not enumerate other users' subscriptions.
- **No auto-request.** The permission prompt is user-initiated from the settings affordance ([ui/index.md §8.7.2](ui/index.md#872-user-menu)); the server never pushes a registration on login.
- **Dispatch-time pruning.** A subscription the browser reports permanently dead at dispatch is removed server-side — housekeeping, not a user-facing operation.
- **Mute interaction.** `pushMuted = true` suppresses delivery to every subscription the user owns; rows are retained, so unmuting restores delivery without a re-subscribe.
- **Rate limiting.** Mutation paths (`POST`, `DELETE`) share a per-session mutation bucket ([architecture.md §12.2 rate-limit config](architecture.md#122-company-configurable-settings) `[C]`); exceeding returns `429 RATE_LIMITED`. The VAPID public-key read is not rate-limited (unauthenticated, GET-only, 5-minute cache).
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED` (subscribe / unsubscribe only; the VAPID read is unauthenticated).
  - Malformed `endpoint` / `keys` → `422 VALIDATION_ERROR`.
  - `endpoint` exceeds 2048 characters, `keys.p256dh` or `keys.auth` exceeds 512 characters, or `endpoint` is not a syntactically valid URI → `422 VALIDATION_ERROR` (bounded to protect the subscription table from pathological input).

Design notes:

- **One channel, typed events.** All event kinds ride a single response stream and are discriminated by the `event:` field. v1 catalog:
  - `storage_usage_changed` — emitted post-commit from every byte-moving mutation site ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Consumers: Footer badge, DatenView row ([AC-450](verification.md#1529-storage-usage)).
  - `project_changed` — emitted post-commit from every project-row mutation site ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Consumers refetch the project list and detail.
  - `attachment_changed` — emitted post-commit from every attachment mutation that changes a project's attachment list ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)). Co-emitted with `storage_usage_changed`. Consumers refetch the per-project attachment list(s). Pinned by [AC-336](verification.md#1528-realtime-events).
  - `invoice_changed` — emitted post-commit from every invoice-row mutation site ([architecture.md §11.14](architecture.md#1114-invoice-domain)): draft CRUD, issue, cancel. Consumers refetch the invoice list / detail read endpoints in [§14.2.14](#14214-invoice-operations).
  - `audit_changed` — emitted post-commit once per committed `audit_log` row, via the notification publisher's `onAuditCommitted` hook ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)). Every audited domain mutation routes through the single-write-path helper, so this one coarse signal covers every activity-feed surface. Consumers refetch the audit read endpoint in [§14.2.8](#1428-audit-log).
  - `data_exchange_job_changed` — emitted post-write on every full-account export / import job lifecycle transition and a throttled subset of progress updates ([architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel), [data-model.md §5.18](data-model.md#518-data-exchange-job-entity)). Consumers refetch the active job over [§14.2.4](#1424-unified-data-exchange). Pinned by [AC-333](verification.md#1514-data-exchange).

  The catalog is open-extensible per [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md) — new event names land here as the consuming surfaces are specified, without new infra.

- **Payload shape.** Each event is an invalidation hint, not a data payload. The `data:` line carries a small typed JSON envelope (e.g. `{ "type": "storage_usage_changed" }`, `{ "type": "project_changed" }`, or `{ "type": "invoice_changed" }`) that mirrors the event name; it is forward-compatible with carrying a non-sensitive correlation field if a consumer ever needs one. Sensitive content is never on the wire — the client refetches via the gated read endpoint that already serves it (`storage_usage_changed` ⇒ refetch the storage totals; `project_changed` ⇒ refetch the project reads; `invoice_changed` ⇒ refetch [§14.2.14](#14214-invoice-operations)). Single source of truth, no two-channel sync.
- **Authorization model.** Authentication at the channel; authorization at the consumer endpoint. Events broadcast to every connected authenticated session — event names carry no information beyond "a thing of kind X changed", and the role-leakage tradeoff is acknowledged and accepted under the project's threat model in [ADR-0025](../adr/0025-realtime-ui-invalidation-via-sse.md). Sensitive content remains behind the consumer endpoints' role gates (e.g. `data:export` for the storage totals, [§14.3](#143-authorization-rules)).
- **Heartbeat.** A 25-second comment line (`:` keepalive) defeats reverse-proxy and browser idle disconnects. The interval is configurable **[C]** ([architecture.md §12.2](architecture.md#122-company-configurable-settings)) — default 25 seconds, bounded 1 s … 600 s.
- **Mid-stream session re-validation.** The authentication preHandler runs once at connect time, so the server bounds a held stream's lifetime to the session that authorized it. Each heartbeat tick re-validates the session ([CWE-613](https://cwe.mitre.org/data/definitions/613.html)); a deleted row (logout / reaper / `UserService.deactivateUser` cascade), an `expiresAt` in the past, or `users.active = false` ends the response stream within one heartbeat interval. Architectural detail in [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel); verification in [§15.28](verification.md#1528-realtime-events) AC-275.
- **Reconnect semantics.** Browser-native auto-reconnect via `EventSource` at the implementation-defined reconnection time mandated by the WHATWG SSE spec (overridable by the server's `retry:` field, not used here). No `Last-Event-ID` replay — events are invalidation hints, not a log; on reconnect the client refetches state via the existing read endpoints. Server restart drops every connection; clients reconnect and refetch (acceptable, parity with [ADR-0021](../adr/0021-audit-log-and-notifications-single-write-path.md)'s in-process publisher).
- **Reverse proxy posture.** Caddy auto-flushes responses with `Content-Type: text/event-stream`; the deployment configuration carries an explicit `flush_interval -1` directive on the `/api/events` upstream as defensive belt-and-suspenders ([architecture.md §11.6](architecture.md#116-deployment-topology), [architecture.md §11.13](architecture.md#1113-realtime-invalidation-channel)).
- **No caching contract.** No `Cache-Control` headers. The protocol is incompatible with caching by design.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`. The connection is rejected; no stream begins.
- **Verification.** The channel shape, auth, broadcast reach, heartbeat, and per-emitter delivery are pinned by [§15.28](verification.md#1528-realtime-events) — `storage_usage_changed` emission by AC-270, `project_changed` emission by [AC-276](verification.md#1528-realtime-events), `attachment_changed` emission by [AC-336](verification.md#1528-realtime-events). The subscribe-side coverage guard (every catalog event has ≥1 client subscriber) is pinned by [AC-338](verification.md#1528-realtime-events). Consumer-side refresh behavior and the multi-user value tests live in [§15.29](verification.md#1529-storage-usage) (storage usage), [AC-277](verification.md#1528-realtime-events) (project lifecycle), and [AC-337](verification.md#1528-realtime-events) (attachments).

Design notes:

- **Number allocation is part of issuance, not creation.** A draft has no `number`; issuance is the only path that allocates. The row-exclusive lock on `invoice_sequence` (taken by the atomic `INSERT … ON CONFLICT … DO UPDATE … RETURNING` — [data-model.md §6.13](data-model.md#613-gapless-sequence-allocation)) is held until the issuance transaction commits, so a failure at any later step (render, binary write, audit) returns the value to the sequence — gaplessness is by construction.
- **Snapshot moment is the issue call, not the draft.** Drafts read live `company_profile` and `customers` to pre-fill the working values; the actual snapshot onto `Invoice.issuer` / `Invoice.recipient` happens at the issue call. A draft created today and issued next month carries next month's company profile (per [data-model.md §5.17](data-model.md#517-company-profile-entity)). Field-level overrides on the draft's recipient are explicit and ride through to the snapshot.
- **Pre-issuance validation.** The issue call rejects when (a) the `company_profile` row lacks a required field ([data-model.md §5.17](data-model.md#517-company-profile-entity); `COMPANY_PROFILE_REQUIRED`), (b) `performanceDate` is null (`VALIDATION_ERROR`), (c) `lines` is empty (`VALIDATION_ERROR`), (d) the parent project is not in `rechnung_faellig` (`INVOICE_PROJECT_STATE`), (e) the draft has already been concurrently mutated to a non-draft state (`CONFLICT`), or (f) a stored line or a derived total breaks a §5.15 rule ([AC-384](verification.md#1530-invoices); `VALIDATION_ERROR`).
- **Line totals are server-derived.** Create draft and Update draft take lines without `lineTotal`; the server derives it from `quantity` and `unitPrice` ([data-model.md §5.15](data-model.md#515-invoice-entity)). A `lineTotal` sent by the client is ignored; a `unitPrice` with more than 4 decimals is rejected.
- **Edit optimistic concurrency.** Update draft, Delete draft and Issue invoice require `expectedVersion`; check order per [data-model.md §6.4](data-model.md#64-concurrency). A rejected issue writes nothing and allocates no number.
- **Calendar-valid dates.** Every `YYYY-MM-DD` field on the wire (`performanceDate`, `issueDate`, …) must round-trip exactly through a calendar-arithmetic check on create / update. A structurally valid but calendar-invalid date (e.g. `2026-02-30`, `2025-04-31`) is rejected `422 VALIDATION_ERROR` rather than silently normalized by `Date` parsing. Silent normalization would land in the immutable issued snapshot, `factur-x.xml`, and the rendered PDF — a §147 AO / GoBD defect.
- **Cancellation creates a sibling, not a soft-delete.** Issued invoices are write-once at the persistence layer ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)); the only mutation allowed is the cancellation flip on the original row's `status`, paired with the Storno row's creation. Cancelling an already-cancelled row returns `INVOICE_ALREADY_CANCELLED` (`409`).
- **PDF download contract.** The PDF/A-3 bytes ride the same e2e-encryption pipeline as attachments ([ADR-0024](../adr/0024-binary-attachment-e2e-encryption.md)) — encrypted at issuance, stored as ciphertext. This gated route is their only read path: the attachment surface never addresses a rendered invoice PDF ([AC-364](verification.md#1530-invoices)). The route returns either the decrypted bytes or a presigned-GET URL paired with the unwrapped DEK material; the transport is implementation-defined.
- **Audit ancestor.** Every invoice mutation writes an `audit_log` row through `mutate()` ([architecture.md §11.3](architecture.md#113-state-layer-behavioral-contract)); the row's `entityType = 'invoice'`, `entityId = <invoice id>`, ancestor `('project', projectId)` ([architecture.md §11.12](architecture.md#1112-audit-ancestor-link)). The project-detail activity feed surfaces invoice events alongside attachments and project transitions in one indexed predicate.
- **SSE.** Issue, cancel, draft CRUD all emit `invoice_changed` post-commit per [api.md §14.2.13](#14213-realtime-events); the client refetches the gated list / detail endpoint. The event name is registered with the SSE event-name registry alongside `storage_usage_changed` and `project_changed`.
- **Worker exclusion.** Worker holds no invoice permission. The repository-predicate scope ([ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md)) excludes invoices from worker reads via absence of a `project_worker` scope path; worker writes are gated by the permission matrix below.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Caller lacks the relevant invoice permission → `403 NOT_PERMITTED`.
  - Update / delete on a non-draft row → `422 VALIDATION_ERROR` with `code = INVOICE_FROZEN`.
  - Update / delete / issue with a stale `expectedVersion` → `409 CONFLICT` with `code = VERSION_CONFLICT`; a missing one → `422 VALIDATION_ERROR`.
  - Issue on a draft whose project is not in `rechnung_faellig` → `409 CONFLICT` with `code = INVOICE_PROJECT_STATE`.
  - Create / update with a `taxMode` outside §5.15 `TaxMode` → `422 VALIDATION_ERROR`.
  - Create / update / issue whose lines or derived totals break a §5.15 rule ([AC-384](verification.md#1530-invoices)) → `422 VALIDATION_ERROR`.
  - Issue with an incomplete company profile → `422 VALIDATION_ERROR` with `code = COMPANY_PROFILE_REQUIRED` and `details.missingFields` enumerating the missing field names.
  - Issue / cancel on a missing id → `404 NOT_FOUND`.
  - Cancel on an already-cancelled invoice → `409 CONFLICT` with `code = INVOICE_ALREADY_CANCELLED`.
  - Cancel on a draft → `409 CONFLICT` with `code = INVOICE_NOT_ISSUED`.
  - Download PDF on a draft → `409 CONFLICT` with `code = INVOICE_NOT_ISSUED`.
  - Bulk export supplying both selectors, or neither → `422 VALIDATION_ERROR`.
  - Bulk export whose id selection includes a draft → `422 VALIDATION_ERROR` with `code = DRAFT_NOT_EXPORTABLE` and `details.invoiceId` naming the draft.
  - Bulk export whose filter matches more rows than the server's ceiling → `422 VALIDATION_ERROR` with `code = EXPORT_TOO_LARGE` and `details.total` / `details.cap`.

- **Bulk export decides its status before it streams.** Every selected invoice is resolved and its bytes obtained before the first byte of the archive is written. Once the archive begins streaming the status code is already committed, so a fault discovered mid-build can only reach the client as a truncated download — which is indistinguishable from a dropped connection. The ceiling on the selection exists to keep that pre-resolution bounded.

Singleton-row CRUD for the tenant's company identity. Entity in [data-model.md §5.17](data-model.md#517-company-profile-entity).

Design notes:

- **Singleton, no POST / DELETE.** The row is pre-seeded by the baseline migration with empty mandatory fields ([data-model.md §5.17](data-model.md#517-company-profile-entity)); the API exposes a read and an upsert only. Trying to create a second row or delete the row is not addressable.
- **Owner-only writes.** Reads are gated by an authenticated session (every authenticated role may read — the profile is referenced by invoice rendering and by the data view); writes require the owner role. The single permission is folded into the owner-only role check (no separate `company_profile:read` / `company_profile:write` keys are introduced — adding one for every owner-only singleton dilutes the permission catalog). The route layer enforces the role check; the service layer rejects non-owner writes defensively.

- **Audit posture.** Each upsert produces one `audit_log` row via the single-write-path helper. Ancestor pair is null (top-level entity, parity with `customer` / `user`).
- **SSE.** Company-profile changes do not emit `invoice_changed` — issued invoices snapshot their issuer at issuance time and are unaffected by subsequent profile edits. The Daten view's company-profile form refetches on its own form-save success.
- **Error paths** (mapped to the categories in [§14.4.1](#1441-error-categories)):
  - Missing or expired session → `401 UNAUTHENTICATED` / `SESSION_EXPIRED`.
  - Non-owner caller on PUT → `403 NOT_PERMITTED`.
  - Stale `expectedVersion` → `409 CONFLICT` with `code = VERSION_CONFLICT`; nothing is written.
  - Body with an empty required field, or any field violating its schema (length, type, format) → `422 VALIDATION_ERROR` with `details` naming the offending field path.

Design notes:

- **Data exchange permissions are distinct from entity read/write permissions.** `data:export` gates the unified export ([§14.2.4](#1424-unified-data-exchange)); `data:restore` gates the unified import. Granting `project:read` does not imply `data:export`.
- **`notifications:manage` is admin-only.** The rule-editor surface ([§14.2.9](#1429-notification-rules)) is admin-only (owner under the default matrix, per [ADR-0023](../adr/0023-notification-rules-db-stored-closed-event-catalog.md)); rule changes affect who-sees-what platform-wide, so this aligns with `user:manage`.
- **`data:restore` is owner-only.** The import destroys or replaces business data in a single transaction — a destructive operation, reserved to the most privileged role consistent with `customer:delete`, `user:delete`, and `project:purge`.
- **Audit read is a single permission; visibility is narrowed by orthogonal scope predicates at the repository layer.** `audit:read` admits a caller to the audit surface at all. Destructive-action visibility is not a second permission: it is the `auditDestructiveScopeForCaller` predicate defined in [§14.2.8](#1428-audit-log) — owner gets a null filter; every other role gets a `WHERE` fragment excluding destructive entries. This follows [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md)'s decision that permissions stay coarse and scope is orthogonal to capability — encoding scope in the permission catalog would conflate _capability_ with _extent_.
- The API must be designed so that scoping reads to a subset (e.g. "projects assigned to user X") is an additive query filter on the list operation, not a restructuring of the endpoint.
- **Holding `project:read` does not imply unscoped access to every project; holding `customer:read` does not imply unscoped access to every customer.** For workers, reads (list and get) are scoped by caller identity — restricted to projects where the worker is in `project_workers`, and to customers referenced by those projects. Owner and office remain unscoped. Exactly one `project:read` and one `customer:read` exist in the matrix — this is observable in the table above. Bookkeeper has unscoped project and customer read as an MVP placeholder until an invoice-oriented view is introduced (see [index.md §4.2](index.md#42-users)). See also [AC-145](verification.md#1521-role-scoping), [AC-146](verification.md#1521-role-scoping), [AC-147](verification.md#1521-role-scoping), [AC-148](verification.md#1521-role-scoping).
- **Attachment operations.** View, list, download and ZIP need `attachment:read`; upload `attachment:write`; hide `attachment:hide` — a worker only their own uploads within the grace window ([AC-411](verification.md#1526-attachments)); Papierkorb list and restore `attachment:trash`. A worker reaches only attachments of projects they are assigned to ([AC-410](verification.md#1526-attachments)).
- **Project operations.** Create needs `project:create`; edit and assigned workers `project:update`; dates `project:dates`; transitions `project:transition`; archive and restore `project:delete`; permanent delete `project:purge`.
- **Storage usage.** The totals ([data-model.md §5.14](data-model.md#514-storage-usage)) need `data:export`. A project's own totals need what reading that project needs.
- **Invoice permissions follow the coarse-capability + scope-predicate pattern.** `invoice:read` and `invoice:write` are coarse permissions; worker exclusion is by absence of a `project_worker` scope path on the invoice row (the repository predicate returns the empty set for worker, parallel to attachments — [ADR-0019](../adr/0019-worker-data-scoping-repository-layer-predicate.md)). The bookkeeper carries `invoice:read` so the bookkeeper-oriented view (the kickoff calls for an invoice-oriented bookkeeper surface — [index.md §4.2](index.md#42-users)) reads from the same gate; bookkeeper still has no write. Owner and office are unscoped.
- **Company-profile access has no dedicated permission key.** Reads are open to every authenticated role (the profile is referenced by invoice rendering and by the data view); writes are owner-only and enforced via the existing owner-role check at the route layer. Introducing `company_profile:read` / `company_profile:write` would dilute the permission catalog with single-singleton keys; the owner-only invariant is the same shape as `data:restore` and is enforced the same way (role check, not a fine-grained permission).
- Authorization checks must be enforced server-side. Client-side UI hiding (e.g. hidden buttons) is a UX convenience, not a security measure (see [architecture.md §13.6](architecture.md#136-security)).

### 14.4 Error Handling

Every error response carries two components:

| Component                  | Purpose                               | Example                                                   |
| -------------------------- | ------------------------------------- | --------------------------------------------------------- |
| **Machine-readable code**  | Programmatic handling by the client   | `INVALID_CREDENTIALS`, `SESSION_EXPIRED`, `NOT_PERMITTED` |
| **Human-readable message** | Display to the user (German, **[C]**) | `"Anmeldung fehlgeschlagen"`, `"Sitzung abgelaufen"`      |

An optional third component, `details`, may carry structured validation information (e.g., field-level errors from schema validation). Clients should handle its absence gracefully.

#### 14.4.1 Error Categories

The API must distinguish the following error categories. Each category has distinct client-side handling (see [ui/behavior.md — Asynchronous Mutation Behavior](ui/behavior.md#95-asynchronous-mutation-behavior)).

| Category                 | Meaning                                                                                                                                                                                                                                                         | Client behavior                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authentication error** | Credentials invalid, session expired, or session absent.                                                                                                                                                                                                        | Redirect to login screen. Show expiry message if session was previously valid.                                                                                 |
| **Authorization error**  | User is authenticated but lacks permission for the requested operation (e.g., changing another user's password).                                                                                                                                                | Show error message. Do not redirect to login.                                                                                                                  |
| **Validation error**     | Request is malformed or violates business rules (e.g., transition from `erledigt`, missing required field, invalid dates).                                                                                                                                      | Show error message. Revert optimistic update if applicable.                                                                                                    |
| **Not found**            | The requested entity (project or user ID) does not exist.                                                                                                                                                                                                       | Show error message. Re-fetch project list to sync state.                                                                                                       |
| **Route not found**      | No handler is registered for the request's method and URL — an unknown URL, or a known one under a verb it does not serve. Distinct from "Not found" above — the latter signals a known endpoint with an absent entity; this signals a stale client or a probe. | Show generic error message. Do not redirect.                                                                                                                   |
| **Gone**                 | The entity existed but is permanently unavailable; retry will not help (e.g., a Papierkorb row whose source bytes were lifecycle-reaped ahead of the row reaper, see [AC-424](verification.md#1526-attachments)).                                               | Show error message. Do not retry.                                                                                                                              |
| **Conflict**             | The mutation cannot proceed because the resource state has changed since it was read (e.g., concurrent state transition) or the operation conflicts with related state (e.g., deleting a customer with active projects).                                        | Refetch resource state. Optionally retry against the new state.                                                                                                |
| **Idempotency conflict** | A create request carried a client-supplied `id` that already identifies a row, but one or more participating fields in the request body differ from the stored row ([AC-127](verification.md#1517-data-integrity)).                                             | Close the create form, refresh the affected list, surface the message. Do not retry the same id with the same body — the request is ambiguous by construction. |
| **Server error**         | Unexpected internal failure.                                                                                                                                                                                                                                    | Show generic error message. Do not expose internal details.                                                                                                    |
| **Rate limited**         | Too many requests in the configured time window.                                                                                                                                                                                                                | Show retry message. Back off before retrying.                                                                                                                  |

The full set of machine-readable error codes: `INVALID_CREDENTIALS`, `UNAUTHENTICATED`, `SESSION_EXPIRED`, `NOT_PERMITTED`, `VALIDATION_ERROR`, `CONFLICT`, `IDEMPOTENCY_CONFLICT`, `VERSION_CONFLICT`, `NOT_FOUND`, `ROUTE_NOT_FOUND`, `GONE`, `RATE_LIMITED`, `SCHEMA_VERSION_MISMATCH`, `TARGET_NOT_EMPTY`, `RESTORE_CONFIRMATION_MISMATCH`, `MISSING_USER_REFS`, `EXPORT_JOB_ACTIVE`, `IMPORT_JOB_ACTIVE`, `EXPORT_JOB_NOT_READY`, `UPLOAD_OFFSET_CONFLICT`, `UPLOAD_TOO_LARGE`, `UPLOAD_NOT_ACCEPTED`, `BULK_LIMIT_EXCEEDED`, `DEK_UNWRAP_FAILED`, `INVOICE_FROZEN`, `INVOICE_PROJECT_STATE`, `INVOICE_NOT_ISSUED`, `INVOICE_ALREADY_CANCELLED`, `DRAFT_NOT_EXPORTABLE`, `EXPORT_TOO_LARGE`, `COMPANY_PROFILE_REQUIRED`, `CUSTOMER_HAS_INVOICES`, `PROJECT_HAS_INVOICES`, `USER_HAS_INVOICES`, `IMPORT_DROPS_ISSUED_INVOICES`, `SERVER_ERROR`.

<!-- CHECKED:error-codes:END -->

`EXPORT_JOB_ACTIVE` / `IMPORT_JOB_ACTIVE` (409) signal a create request colliding with an export / import job already `pending` or `running` ([§14.2.4](#1424-unified-data-exchange) — "Jobs — one active per kind"); the response carries the active job's id so the client re-attaches rather than starting a second. `EXPORT_JOB_NOT_READY` (409) is a download requested before the build finished. `UPLOAD_OFFSET_CONFLICT` (409) is a resumable-upload chunk PATCHed at an offset other than the server's current one. `UPLOAD_NOT_ACCEPTED` (409) is a chunk PATCHed to an import job that is no longer `pending` — the upload already completed (the job is `running` or terminal), or the id is not an import job at all; the normal client loop ends at `Upload-Length` before the flip, so this guards direct API misuse (e.g. PATCHing an export job's id to fire a bogus restore). All five are conflict-category codes — the client resolves them by re-reading job / upload state, not by re-authenticating. `UPLOAD_TOO_LARGE` (413) is a resumable-upload chunk whose bytes would extend past the declared `Upload-Length`; the server offset does not advance and the client retries with at most the remaining length.

`VERSION_CONFLICT` (409) is a versioned edit whose `expectedVersion` no longer matches the stored row ([data-model.md §6.4](data-model.md#64-concurrency)); nothing was written. A conflict-category code, distinct from `CONFLICT` so the client runs stale-write recovery ([ui/behavior.md §9.5](ui/behavior.md#95-asynchronous-mutation-behavior)) rather than a generic refetch.

`MISSING_USER_REFS` is a specialization of the validation-error category — same client behavior (show error, no redirect, revert any optimistic UI), distinct code so the operator UI can render the targeted "re-export from a complete source" remediation copy. With `users` in the envelope ([data-model.md §5.8](data-model.md#58-export-envelope)), this code surfaces only on hand-edited / partial / third-party-produced envelopes whose audit-field user-id values point outside the envelope's own `users[]` slot — defense in depth on a path that no normal export produces. See [§14.2.4](#1424-unified-data-exchange) for the validation semantics.

The error body uses the standard `{ code, message, details }` shape. The `details` payload for `MISSING_USER_REFS` is:

```typescript
{
  missingUserIds: string[];                            // deduplicated
  references: { path: string; userId: string }[];     // one entry per offending reference site
}
```

`missingUserIds` is the deduplicated list of user ids the envelope references but `envelope.users[]` does not contain. `references` carries one entry per offending envelope reference site (e.g., `{ path: "projects[3].createdBy", userId: "abc" }`) so the operator can locate every offending row without guessing; duplicate user-id references across different sites produce one entry per site. `MISSING_USER_REFS` is raised only when at least one referenced user id is absent from `envelope.users[]`, so both fields are non-empty whenever the code is returned. The `path` shape (e.g. `customers[2].createdBy`, `project_workers[5].userId`, `invoices[7].createdBy`) matches the intra-envelope issue path shape used for `VALIDATION_ERROR`. Error `details` keys in this spec are camelCase.

`DEK_UNWRAP_FAILED` is also a specialization of the validation-error category (`422`) — a per-row attachment envelope cannot be unwrapped against the currently-loaded binary identity (corrupt envelope or partial key rotation). The Service Worker translates the code to the [AC-244](verification.md#1526-attachments) "Schlüssel nicht verfügbar" placeholder render path.

The invoice-domain codes are specializations of the validation-error and conflict categories:

- **`INVOICE_FROZEN`** (`422`) — mutation rejected because the invoice is `issued` or `cancelled` ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)). Client should refetch and present a read-only viewer.
- **`INVOICE_PROJECT_STATE`** (`409`) — issue rejected because the parent project is not in `rechnung_faellig`. Client refetches the project status and surfaces the mismatch (the project may have moved while the draft was open).
- **`INVOICE_NOT_ISSUED`** (`409`) — cancel / download-PDF rejected on a draft. Client surfaces the message; the affordance should not have been presented (a client-state-drift indicator).
- **`INVOICE_ALREADY_CANCELLED`** (`409`) — cancel on a row whose `status` is already `'cancelled'`. Idempotent intent is acceptable, but the route does not silently succeed — the operator's view of the invoice should be refreshed before a re-cancel attempt.
- **`COMPANY_PROFILE_REQUIRED`** (`422`) — issue rejected because the singleton `company_profile` row lacks a required field ([data-model.md §5.17](data-model.md#517-company-profile-entity)). `details.missingFields` enumerates the missing field paths (e.g. `["companyName", "address.zip", "ustId"]`). Client routes the owner to the Daten view's company-profile form ([ui/daten.md §8.11.4](ui/daten.md#8114-company-profile)).
- **`CUSTOMER_HAS_INVOICES`** (`409`) — customer hard-delete rejected because at least one of the customer's projects (active or archived) carries an **issued or cancelled** `Invoice` row ([data-model.md §6.9](data-model.md#69-soft-deletes)). Draft invoices do not trigger this code — they cascade with the project on the customer's atomic-purge cascade. `details.invoiceCount` carries the count of issued + cancelled rows; the client surfaces the German invoice-notice copy ([ui/management.md §8.9.5](ui/management.md#895-delete-customer)) and refuses to send the delete. There is no remediation path — issued / cancelled rows are subject to §147 AO retention.
- **`DRAFT_NOT_EXPORTABLE`** (`422`) — bulk export rejected because at least one requested invoice id resolves to a draft. Drafts carry no rendered PDF, so including one would either bundle an empty document or fail mid-stream after bytes have already left the wire. `details.invoiceId` is the offending draft so the client can target the row in the user's selection. Raised in ids-mode only; in filter-mode drafts are silently outside the filter. See [§14.2.14](#14214-invoice-operations).
- **`EXPORT_TOO_LARGE`** (`422`) — bulk export rejected because the filter matches more invoices than the server will bundle into one archive. `details.total` is the matched-row count and `details.cap` the ceiling, so the client can phrase a precise message. The caller narrows the filter (typically by year) and retries. See [§14.2.14](#14214-invoice-operations).
- **`PROJECT_HAS_INVOICES`** (`409`) — project hard-delete (`DELETE /api/projects/:id/purge`) rejected because the project carries any **issued or cancelled** `Invoice` row ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices), [§6.6](data-model.md#66-referential-integrity)). Draft invoices on the project cascade-delete with the purge and do not trigger this code. `details.invoiceCount` carries the count of issued + cancelled rows. Distinct from `CONFLICT` (used for purging a non-archived project, AC-503) so the client can render the targeted invoice-notice copy rather than the generic archive-first hint.
- **`USER_HAS_INVOICES`** (`409`) — user hard-delete rejected because an **issued or cancelled** `Invoice` row references the user as `createdBy` or `updatedBy` ([data-model.md §6.9](data-model.md#69-soft-deletes)). References on drafts do not trigger this code. `details.invoiceCount` carries the count of those rows. The German message points to deactivation as the remedy.
- **`IMPORT_DROPS_ISSUED_INVOICES`** (`409`) — `override` import rejected because the target holds an **issued or cancelled** `Invoice` that the envelope does not carry with the same id and number ([data-model.md §6.14](data-model.md#614-immutability-of-issued-invoices)); no writes. Draft invoices do not trigger this code. The remedy is an archive exported after the latest issuance. The import job terminates `failed` with the code's message as `error_detail`.

#### 14.4.2 Error Principles

- **Authentication errors are distinguishable from authorization errors.** An expired session must not produce the same error as an insufficient permission — the client handles them differently (redirect vs. inline message).
- **Validation errors are structured.** When a mutation is rejected for business rule violations, the error must identify which rule was violated (e.g., "cannot transition from terminal state") so the client can render a meaningful message.
- **Error messages never leak internal details.** No stack traces, database field names, table names, file paths, or query information in any error response. This applies to all error categories including server errors.
- **HTTP statusCode reflects the failure class.** A request rejected at the transport layer (malformed body declared as JSON, payload exceeding configured limits, unsupported media type, request whose method and URL match no registered handler) preserves the 4xx HTTP statusCode native to that failure and surfaces a stable machine-readable code. Transport-layer rejections are never collapsed into a 5xx response, and they are not logged at the operational `error` level (used to back 5xx alerting on logs). Rationale: 5xx must mean "the server failed", not "the client made a recoverable mistake"; conflating the two — either through the wire response or through the log severity — trains operators to ignore real 5xx incidents.
